# Контракты параллельной реализации CHAT-A/B/C

Владелец: CHAT-A. 2026-10-14, Europe/Istanbul. READY означает стабильный интерфейс для реализации, а не runtime qualification. Все новые возможности включаются только явно квалифицированным runtime; v1/v2 originals и receipts сохраняют прежнюю семантику.

## K1 r1 — READY, потребители B/C

Общий envelope: `binding` — прежние семь полей SyncRootBinding; новые операции дополнительно несут `namespace: { codec: "legacy" | "portable_v1", policyHash: <sha256> }`. Codec/policy проверяются по durable root policy, не по декларации клиента. Legacy root сохраняет прежнюю семантику.

- `POST /sync/v1/roots/:rootId/directories/batch`: `{binding, items:[{ref,input,parentRef?}]}`. input — существующий CatalogFolderRequestV2. ref — уникальная ASCII-строка 1–64; parentRef ссылается только на предыдущий элемент. При parentRef сервер заменяет parentId/parentTopology результатом указанного original и его topology. Неуспешный dependency даёт `dependency_failed`, остальные независимые элементы продолжаются. Ответ `{schema:"saturn.folder-batch-result.v1",items:[{ref,outcome?,code?}]}`. Ограничения: 500 items, 4 MiB распакованных метаданных. Повтор всегда с исходными operationId/idempotencyKey.
- `POST /sync/v1/roots/:rootId/mutations/execute` и `/mutations/status`: `{binding,namespace,input}`. input — `SyncMutationInput` из `packages/contracts/src/sync-extensions.ts`; original identity и CAS неизменяемы. Результат `SyncMutationStatus`. Разрешённые kind: `move`, `quarantine-delete`, `restore`, `metadata-patch`, `create-empty`, `clone-content`, `availability`. `availability` — только внутренний protection caller. Pluto не получает move/delete/restore.
- `POST /sync/v1/roots/:rootId/content/lookup`: `{binding,sizeBytes,sha256}`; ответ `{reference:null|{nodeId,contentVersionId,metadataVersion,sizeBytes,sha256}}`. Поиск только в текущем авторизованном root, без global existence oracle. Clone связывает именно version, не изменяемый путь.
- Expected: `{kind:"absent"}` или `{kind:"version",node_id,version}`. Для move/delete/meta/restore обязателен version. Move destination обязан быть свободен; замещение — отдельный явно согласованный original. Delete только leaf/postorder; backend quarantine и tombstone сохраняют историю.
- Metadata-patch передаёт `contentVersionId` и `sha256` как proof неизменности, и `modifiedAt` в UTC. Совпадение mtime не является proof. Empty использует обычный durable mutation без upload session.
- `portable_v1`: Unicode NFC; запрещены control/surrogates, /\\, Windows `< > : " | ? *`, trailing dot/space, . и .., DOS device stems (CON, PRN, AUX, NUL, COM1..9, LPT1..9, включая superscript ¹²³); максимум 255 Unicode scalars / 1020 UTF-8 bytes. Collision key — NFC + ASCII A–Z→a–z; не locale casefold. Любое изменение существующего имени требует migration plan; молчаливая нормализация запрещена.

## K1 r2 — READY, дополнение r1 (потребители B/C)

Все r1 envelopes/receipts сохраняются. Текущая capability сообщает `revisions:{K1:2,K2:2,K3:2,K4:1}`; потребители должны принять K1 r2. Ниже зафиксирован прежний пример K3 r2 с K1 r1 для истории; revision каждой группы обновляется независимо.

- `POST .../delete-plans/approve`: `{binding,namespace,plan:{schema:"saturn.delete-plan.v1",planId:<UUID>,planDigest:<SHA256>,items:[{nodeId:<UUID>,version:<UUID>}]}}`. 1–500 уникальных nodes, неизменный порядок и состав при повторе. Ответ `{schema:"saturn.delete-plan-approved.v1",planId,planDigest,itemCount}`. Требуется действующий Windows device с правом delete; Pluto запрещён. Digest обозначает подтверждённый пользователем клиентский preview, сервер дополнительно связывает точные items, actor, root binding и policy. Каждая версия проверяется до записи approval; mutation заново проверяет CAS и leaf/postorder. Повтор того же approval после потери ACK возвращает receipt, не повторяет проверку уже удалённых items. Чужой actor или изменённый список под прежним planId запрещены. Клиент сохраняет original plan и server receipt **до** отправки mutations с planId. Null planId/null planDigest по-прежнему разрешены для отдельной leaf-операции. Смена binding/policy/версии требует нового preview.
- `POST .../mutations/batch`: `{binding,namespace,items:[{ref,input}]}`, 1–500, unique ref и operationId, 4 MiB decoded metadata. Ответ `{outcomes:[{ref,outcome:<SyncMutationStatus>}|{ref,code}]}`. Независимые элементы исполняются по очереди; ошибка одного не отменяет опубликованные другие. Нет local references и общей транзакции для всего batch. Те же original IDs обязательны при повторе.
- `packages/contracts/fixtures/name-codec-v1.json` — общие неисполненные vectors. Дополнительно действует прежний PostgreSQL `lower(name)` unique constraint: некоторые Unicode-пары могут получить консервативный collision refusal. Migration preview показывает это как отдельный blocker; имена не изменяются автоматически.

## K3 r2 — READY, потребители B/C (r1 сохранён по смыслу, уточнён JSON)

Точный дополнительный JSON capability field:
`extensions: { revisions:{K1:1,K2:2,K3:2,K4:1}, namespace:{codec:"legacy"|"portable_v1",policyHash:"<sha256>"}, minimum_writer:"saturn.namespace-mutation.v1", backend_policy:"managed-exclusive", limits:{metadata_items:500,metadata_bytes:4194304,long_poll_ms:25000,gzip_threshold_bytes:16384,stream_chunk_bytes:4194304,stream_maximum_chunks:256} }`.
Новые features входят в прежний top-level `features` array. Отсутствие extensions означает старую compatibility. `namespace` берётся из current durable root policy. B/C: перейти на K3 r2 при реализации parser; K3 r1 дополнительных полей не фиксировал.

- Старый capability envelope сохранён. Новые features публикуются только после qualification: `changes-wait-v1`, `folder-batch-v1`, `namespace-mutations-v1`, `stream-upload-v1`, `metadata-gzip-v1`, `clone-content-v1`. Дополнительный `extensions` содержит revisions K1–K4, codec/policy, limits. Наличие endpoint без negotiated feature не разрешает его использовать.
- `POST .../changes` сохраняет прежний request и добавляет optional `wait_ms` (0..25000). Пустой feed ждёт bounded poll; разрыв запроса отменяет ожидание. Каждый повтор проверяет binding/ACL/cursor, не удерживает DB transaction. Ответ прежний SyncFeedPage; timeout — пустая страница, не gap. Heartbeat не продлевает absolute cursor lease.
- 429 `admission_full`/`capacity`, 503 `backend_busy`/`backend_draining` дают `Retry-After` integer seconds и `{code,retry_after_ms}`. Повтор использует original operation. 409 `reconciliation_required`/`transfer_unresolved`/`operation_unknown` означает сначала status/recovery; не новую операцию. 409 `binding_mismatch`/`policy_mismatch`/`codec_mismatch` требует rebind/replan. 412 `precondition_failed` — конфликт. 401/403 — остановить авторизованные эффекты. 413 — уменьшить payload без изменения original semantics.
- Gzip только JSON metadata при negotiated feature; рекомендуемый порог >16384 bytes. `Content-Encoding:gzip`, лимиты compressed <=4 MiB, expanded <=4 MiB (для малых endpoints сохраняется их меньший лимит), depth<=32, items<=500. File chunks/batch binary frames не сжимаются. Canonical original hash не зависит от HTTP encoding.
- Статусы phases: queued/captured/received/written/verified/published. Received/written не означают publication. UNKNOWN сохраняется до доказанного recovery. Метрики без путей/credentials/content: counts, bytes, oldestPendingMs, queue/pool/SQL/storage wait, retries, pressure, backend owner state.
- Shutdown/profile switch: admission close → drain/checkpoint → close old connections → durable stopped receipt → новый owner. Timeout SQL lease не разрешает takeover. Новые root features OFF до qualification. Managed roots имеют managed-exclusive backend policy без внешних writers; observation capability — отдельное квалифицированное расширение.

## K4 r1 — READY, потребитель C (host), владелец A (schema/client)

Единственная TypeScript wire schema: `packages/contracts/src/storage-verifier.ts`; JSON UTF-8 с точными decimal strings. `POST /v1/verify`, Content-Type application/json, `Authorization: Bearer <protected shared secret>`. HTTPS обязателен вне loopback; secret не входит в JSON/diagnostics. Host bind/address/root configuration и secret — operator-owned. Request/response не более 64 KiB; maximumBytes <= 1 GiB; timeoutMs 1..30000. Cancellation закрывает client request; host прекращает чтение при disconnect/deadline.

Request `StorageVerifyRequest`: schema `saturn.storage-verify.v1`, requestId UUID, backendIdentity, backendGeneration UUID, ownerId UUID, fencingToken UUID, rootId UUID, operationId UUID, intentSha256, contentVersionId UUID, relativePath, sizeBytes, sha256, maximumBytes, timeoutMs, requireDurability (`readback`|`file-sync`). Path — нормализованный backend-relative, без . / .. / empty segments / backslash / controls; authority host связывает rootId с разрешёнными prefix scopes, включая private operation-owned staging/history при необходимости. Client input path не становится authority.

Response `StorageVerifyResult`: schema `saturn.storage-verify-result.v1`, все identity fields request (без path/limits/timeout/requireDurability), sizeBytes, sha256, durability (`readback`|`file-sync`), checkedAt UTC ISO, status `VERIFIED`. Identity/digest/length обязаны точно совпасть. Host проверяет exact backend/owner/fencing registry до и после чтения; никакой lease-expiry takeover. Проверка no-follow всех ancestors и file handle, stable file identity/size/timestamps до/после, bounded sequential SHA-256. file-sync означает успешный fsync конкретного file handle; совпадение hash само по себе не утверждает durability. Directory durability этим протоколом не обещается.

Ошибки `{code}`: `unsupported` (501), `unauthorized` (401), `scope_denied` (403), `identity_mismatch`/`source_changed`/`verification_failed` (409), `capacity` (429), `cancelled` (408), `verifier_unavailable` (503), `invalid_input` (400). Saturn делает bounded readback fallback при unavailable/unsupported; отказ authority/fencing или mismatch не превращает в VERIFIED. Верификация всегда независима от catalog hash. Host пакет не получает право изменять файлы. Clone в K4 r1 отсутствует; локальный independent copy поддерживает Saturn adapter, SFTP copy fallback остаётся read/write.

## K2 r2 — READY, потребители B/C (заменяет r1 DRAFT)

Shared types: `packages/contracts/src/sync-stream.ts`. Feature `stream-upload-v1`.

- `POST .../stream-uploads/prepare` и `/status`: `{binding,input}`. Input: `{schema:"saturn.stream-upload.v1",operationId:<UUID>,source:{generation:<opaque ASCII 1..128>,witnessSha256:<sha256>},chunkBytes:4194304,prepare:{epoch,bindingVersion,backendIdentity,intent}}`. intent — все прежние поля `saturn.upload-intent.v2`, но `sha256:null`; sizeBytes известен до transfer. Это новая immutable identity; старый sealed original не преобразуется.
- `PATCH .../stream-uploads/chunk`: Content-Type `application/vnd.saturn.sync-stream.v1`. Четыре байта BE metadata length, JSON `{binding,input,chunk:{index,offset,length,sha256}}`, raw bytes. Metadata <=40 KiB, chunk ровно 4 MiB, последний — остаток; index 0..255, offset/length decimal strings. Сервер принимает последовательные offsets; повтор идентичного подтверждённого chunk возвращает прежний ACK без записи bytes. Неподтверждённый reserved chunk даёт UNKNOWN; слепой retry записи запрещён.
- `POST .../stream-uploads/seal`: `{binding,input,seal:{sha256,sourceGeneration,sourceWitnessSha256}}`. Source fields равны immutable input и подтверждены caller после source capture. Whole SHA связывается один раз, после ACK всех chunks. Сервер завершает старым verified/CAS executor с тем же operationId/uploadId; отдельной новой операции/нового idempotency key нет.
- `POST .../stream-uploads/complete`: `{binding,input}` продолжает sealed publication. `/status` никогда сам не публикует.
- Ответ `SyncStreamStatus`: `{schema:"saturn.stream-upload-status.v1",operationId,state,receivedSizeBytes,chunks:[{index,offset,length,sha256}],pendingChunk:null|chunk,finalSha256:null|sha256,publication:null|<existing CatalogUploadStatus>}`. state: RECEIVING/SEALED/PUBLISHING/UNKNOWN/PUBLISHED. Не более256 chunks при server file bound1GiB; Pluto сохраняет256MiB.
- Source mutation до seal → caller сохраняет original deferred, не подменяет source witness. Restart использует только ACK map и ту же доказанную source version. Whole digest после restart восстанавливается отдельным учтённым чтением, не конкатенацией chunk hashes. Старый catalog-upload-v2 остаётся fallback для новых работ при отсутствии capability; accepted stream original требует stream status/recovery.

## K3 operational artifacts (r2, server CLI)

`scripts/sync-lifecycle.mts` принимает protected config `saturn.sync-lifecycle.v1`; команды inspect/pause/checkpoint/backup/migrate-plan/adopt/resume/diagnostics/rollback-plan/handoff/recovery-plan/repair-folder. Подробный порядок и ограничения находятся в `CHAT_A_IMPLEMENTATION_HANDOFF_2026-10-14.md`.

`adopt` создаёт `saturn.sync-adoption.v1` с `planId`, `planSha256`, `treeSha256`, прежним семиполевым `binding`, `device_id`, `backend_identity`, `qualification_receipt_sha256`, `namespace:{codec,policyHash}`, `manifestRoot:{rootId,epoch,bindingVersion,guardRevision,activationReceiptSha256}`. Output artifact дополнительно имеет `runtimeManifestFile`, `manifestRefreshRequired:true`, `automaticActivation:false`. Artifact — результат offline operator action, не замена HTTPS capability/authority. Identity/credentials клиентов сохраняются. Повтор APPLIED plan возвращает сохранённый receipt; новый runtime manifest можно восстановить без повторного physical adoption. Выбранный codec/policy закрепляется в плане; blockers запрещают переход и не переименовывают файлы. Accepted originals перед сменой должны быть завершены либо отдельно разобраны; по возрасту они не удаляются.

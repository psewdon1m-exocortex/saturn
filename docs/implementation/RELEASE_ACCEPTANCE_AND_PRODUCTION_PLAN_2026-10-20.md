# План обязательных исправлений, приёмки и выпуска

Дата: **20 октября 2026**, Europe/Istanbul (UTC+3).
Проекты: **Kernel, Saturn, Neptune, Pluto**.
Статус: **PLAN_ONLY — исполнение не начато**.

Этот документ подготовлен по поручению пользователя. Сейчас разрешены только подготовка документа и ведение журнала. Он **не является командой запускать исправления, тесты, сборки, стенды, коммиты, публикацию или обновление production**.

Решение пользователя: дальнейшую оптимизацию скорости отложить; устранить обнаруженные проблемы, принять выпускаемую систему и подготовить согласованный выпуск. Неподтверждённые результаты не переименовывать в PASS.

## 1. Решения и границы релиза

### 1.1. Что меняется в критериях

- Цели **50 файлов/с**, **6 каталогов/с**, **100 Мбит/с** перестают быть самостоятельными числовыми условиями этого выпуска. Наличие скорости ниже прежней цели само по себе не блокирует выпуск.
- Вместо этих целей действует проверка **сохранения фактически достигнутой производительности**: одинаковый корпус, маршрут, ресурсы и измеритель; исходная сборка против исправленного кандидата. Правило сравнения — раздел 7.
- Сохраняются целостность, права, индивидуальные версии и receipts, восстановление, bounded consumption, совместимость и штатная доступность функций.
- Порог скорости не разрешает ослаблять durability, SHA, CAS, fencing, проверку источника, подписи или миграционные проверки.
- Исторические performance FAIL сохраняются в исходных отчётах. В новом ledger рядом записывается: «прежний числовой порог исключён решением пользователя; проверка регрессии — отдельный результат».
- **Масштаб не отменён:** ранее запрошенные 500000 реальных файлов / минимум 20 ГиБ и минимум 20 одновременно работающих native Pluto backup jobs остаются отдельными условиями совместного прогона. Их нельзя заменить строками SQL, server-only генерацией или числом поставленных в очередь запросов.
- Ограничение больших файлов и количества записей — функциональность, а не fps. Нельзя незаметно вернуть прежний лимит Neptune 1 ГиБ или 1000000 записей.

### 1.2. Состав выпуска

Базовый выбор: выпускать завершённые штатные пути, сохраняя существующие функции. Для каждого включённого режима должен существовать рабочий путь от UI/daemon до физического результата и восстановления.

| Область | В текущий выпуск | Что отложить |
| --- | --- | --- |
| Neptune | Исправленный действующий initial/fresh/batch/fallback, согласование операций root, сохранение originals | Новое ускорение CAS job, SQL coalescing и увеличение concurrency ради fps |
| Pluto | Последний завершённый путь small jobs/receipts/streaming при прохождении приёмки | Непроверенную оптимизацию подготовки родителей; новый CAS job без серверного контракта |
| Web/Drop | Действующие рабочие upload/drain, исправления очереди, SHA/recovery и UI | Незавершённый U03 streaming executor и его новый публичный режим |
| Owner/shared download | Исправленные Range, ZIP/packages, ограниченные потоки, актуальные permissions/accounting | Дальнейшую оптимизацию архивации и SQL ради абсолютных скоростей |
| Kernel | Проверенную цепочку discovery/grant/update, совместимую с выпускаемыми сервисами | Изменения, не нужные для correctness или совместимости этого выпуска |

**Отложенная функция не считается исправленной.** Она фиксируется как `DEFERRED_NOT_SHIPPED`, не рекламируется, не включается capability и не должна требоваться действующему маршруту. Одного выключенного UI недостаточно: проверяются HTTP, worker, restart, retained state и migrations.

Нельзя просто удалить все незакоммиченные изменения U03 или откатить общие файлы: D04 и другие пути используют часть этих исправлений. Состав выделяется по зависимостям. Нельзя исключить уже поддерживаемую функцию без отдельного решения пользователя.

Если принятые пользователем операции требуют незавершённого executor/CAS-контракта и безопасного действующего пути нет, соответствующая интеграция становится обязательной, а не скрытым fallback.

Фактически используемый production backend обязателен в приёмке. Если это SFTP, локальный adapter или контейнерный SFTP не заменяет целевой provider: нужны разрешённый изолированный доступ, доказательство владения/ограничения namespace, host-key validation, fsync/rename и recovery. Успешный password login/root stat не закрывает P4. При отсутствии необходимого доступа фиксируется BLOCKED, доступ не имитируется и чужой пароль не ротируется.

### 1.3. Чего этот план не разрешает

Не возобновлять старые остановленные прогоны и их автоматизации. Не менять рабочие vault/профили, главный сетевой маршрут ПК и чужие стенды. Не выключать Docker Desktop/engine/WSL. Не обходить прежние отказы автоматической проверки удаления/внешнего туннеля. Не публиковать релиз и не менять production по одному факту наличия этого документа.

## 5. Общие правила доказательства

### 5.1. Oracle

Для каждого корпуса до запуска сохранить ожидаемые пути, типы, размеры, SHA-256, пустые каталоги и seed. Для изменяемого корпуса вести независимый журнал ожидаемых поколений, формируемый генератором изменений, а не синхронизатором.

После завершения:

1. Прочитать реальные bytes из конечного backend/обычного download, а не только SQL или кеш клиента; сравнить SHA каждого ожидаемого файла.
2. Сверить точное дерево, отсутствие лишних объектов/версий, актуальные IDs/versions/receipts и parent aggregate.
3. Для overwrite/rename проверить сохранение resource identity по контракту; для replay — отсутствие второго эффекта.
4. Для Drop различать ingress/accepted и конечный `stored`; буфер не является успешным сохранением.
5. Проверить неизменность исходных файлов, кроме явно внесённых генератором изменений. Локальные пользовательские `name (2).md` сохраняются; появление нового необъяснённого дубля — FAIL.
6. Измерить финальную очередь: pending/runnable/UNKNOWN, старейшая операция, cleanup debt. Простое отсутствие ошибок в логах не означает завершение.

100% SHA обязателен для целевого 500k и всех небольших приёмочных корпусов. Выборочное чтение, счётчик опубликованных файлов и правильный размер не заменяют полный readback. Время отдельного oracle записывается отдельно от throughput.

### 5.2. Отказы и сроки

- Каждый fault marker содержит точные process/container/backend IDs, момент включения/снятия и подтверждение реального отказа.
- После восстановления доступного маршрута новый полезный progress на малом корпусе должен начаться **не позднее 60 секунд**, без ручного повторного Sync/re-enrollment.
- Для небольшого фиксированного recovery-корпуса допустимый срок сходимости: `max(120 секунд, 2 × соответствующее fault-free время + 60 секунд)` после восстановления зависимостей. Исходное время и срок записать **до** инъекции; это тестовый критерий, не обещание SLA для произвольного объёма.
- Если требуется явный операторский reconciliation из-за действительно недоказанного физического исхода, безопасность UNKNOWN проверяется отдельно. Такой случай не объявляется автоматическим recovery PASS; процедура reconciliation должна быть воспроизведена и доведена до точного результата без потери originals.
- Длинный поток, у которого поступают bytes, не обрывается общим коротким control timeout. Настоящий idle ограничивается штатным deadline; увеличением таймаута нельзя прятать R03.
- Не моделировать неожиданный исход ответом тестового remote там, где критерий требует реальной записи, разрыва процесса или потери HTTP ACK. Mock-проверки — первый уровень, не последний.

### 5.3. Повторы и экономия времени

- Сначала воспроизвести конкретный дефект. Затем узкое исправление и его тест; после GREEN — непосредственно затронутые интеграционные случаи.
- После каждой правки не запускать общий pipeline.
- Один раз на замороженном RC выполнить обязательные штатные lint/typecheck/build/unit/release checks, предусмотренные текущими CI и qualification policy. Изменение performance-порогов не отменяет policy receipts, подписи и проверки безопасности выпуска.
- Перезапускать только invalidated проверки, но фиксировать зависимость от изменённых исходников/схемы/config. Изменение общего executor/database/storage инвалидирует все затронутые каналы, а не только тест владельца.
- Независимые корректностные lanes могут идти параллельно на собственных БД/roots/профилях. Сравнения скорости выполняются в чистом измерительном окне.
- Не менять используемые запущенными тестами бинарники. Каждый кандидат получает отдельный immutable build directory.

## 6. Адресные тесты дефектов

Все тесты этого раздела обязательны для выпускаемого пути. Статус на дату документа — `NOT_RUN_FOR_RELEASE_CANDIDATE`.

### T01 — агрегаты при параллельных изменениях

**Вход:** собственная production-composed API/worker/реальная PostgreSQL, 10 каталогов, 90 файлов по 1024 байта, независимый manifest. Использовать исходный D04 воспроизводитель `CATALOG-source-1792436055462` как первый RED; сохранить его конфигурацию.

**Действия:** параллельно публиковать через обычные API до 16 пользовательских запросов, сохраняя штатный предел физических workers. После settle проверить root **92160 байт** и суммы каждого предка. Затем увеличить 10 файлов на 1024 байта, перенести 10 файлов в другие родители, удалить другие 10 файлов по штатному контракту. Проверять суммы после каждой фазы. На уменьшенном дереве выполнить 20 независимых повторов с записанными seeds и управляемым перекрытием транзакций.

**PASS:** все суммы точно равны независимому расчёту; текущие bytes/версии совпадают; move не меняет общий объём; replay не увеличивает агрегат второй раз. Нет ручного SQL-пересчёта в качестве «исправления» теста.

### T02 — блокировки предков и DIR-T

**Вход:** исходный D04 deadlock case `bulk-series-DIR-T-P0-1792444218340`; 64 ветви глубиной 16, всего 1024 новых каталога.

**Действия:** параллельно создавать разные ветви общего root штатными запросами с соблюдением parent dependency. На малом дереве отдельно организовать две конкурирующие транзакции, меняющие общих предков, и move между ветвями; 20 повторов. Затем один полный DIR-T, restart API/worker и продолжение ещё 128 каталогов.

**PASS:** точное дерево и aggregates, нет зависшего запроса/необработанного SQL 40P01, нет двойных каталогов. Если дизайн допускает ограниченный повтор откатившейся транзакции — доказать rollback, idempotency, ограниченность повторов и отсутствие нового physical effect. Полный workload заканчивается в установленный тестовый срок.

### T03 — N01 fresh B2 и восстановление без reset

**Вход:** сохранённые `admission-fresh-abba-progress.json`, `cases/native-admission-fresh-b2-512/native.log`, HTTP/SQL evidence и профиль из N01 archive. Исходные архивы не изменять; при необходимости развернуть копию полного NTFS VHD с проверкой identities.

**Действия:** сначала классифицировать исходную первичную ошибку, в том числе readiness/TLS/deadline/SQL и возможное истечение тестового сертификата. Восстановить последовательность A1/B1/B2/A2 на собственных roots, по 512 изменений, без потери контекста retained state. Дополнительно повторить смешанные новые файлы/CAS с одним lost-response-after-commit и restart клиента.

**PASS:** все четыре прохода завершены с полным oracle; типизированная ошибка не замаскирована локальным admission отказом; те же originals возобновлены, лишних версий нет. Отказ из-за fixture закрывается только новым корректным воспроизведением и доказательством причины, не удалением assertion.

### T04 — delete approval, gap и новые изменения

**Вход:** точный сохранённый B05 failure и доступный тестовый профиль; трёхуровневое дерево с 32 файлами, независимый соседний root.

**Действия:** сформировать preview удаления; до approval изменить содержимое одного файла, переименовать другой, внести новое поколение hint/gap. Применить старое approval. Затем получить новое preview и подтвердить актуальный набор. Повторить потерю ответа после удаления и restart; отдельно проверить ACL denied и hardlink/reparse вне root.

**PASS:** stale approval отвергнуто без физического удаления новой/чужой версии; актуальный набор удалён один раз; g+1 не ACK-нут старым ответом; соседний root и originals сохранены. Исторический артефакт, которого нет, не подменяется формальным SKIP: нужен воспроизводитель того же свойства и явное объяснение границы доказательства.

### T05 — root admission и CAS

**Действия:** повторить 34 текущие адресные проверки, затем реальный WindowsSyncService → production API: новый файл + CAS одного родителя, разные родители, несовместимый rename/delete и 32 МиБ stream. Потерять ответ после terminal publication и перезапустить клиент. Старый pending batch должен закончиться после изменения negotiated capabilities без нового operation ID.

**PASS:** совместимые запросы укладываются в объявленные лимиты, несовместимые не перекрываются, UNKNOWN запрещает опасное продолжение; штатная очередь самостоятельно продолжает работу после разрешения исхода. Конкурирующий remote overwrite вызывает определённый conflict, не adoption чужих bytes.

### T06 — SFTP progress и долгий поток

**Действия:** по собственному соединению передать 1 МиБ с положительным прогрессом дольше прежних 32 секунд (контрольный сценарий около 224 секунд); отдельно создать полный idle и затем отмену. Выполнить read и write на реальном применяемом SFTP, с проверкой host key, fsync и новым соединением для readback.

**PASS:** прогрессирующий поток доходит до правильного SHA; idle заканчивается штатной типизированной ошибкой, отмена закрывает реальные handles/слоты; OPEN/CLOSE подтверждены, нет непредусмотренного replay. Точный общий production SFTP проверяется только в изолированном разрешённом namespace.

### T07 — физическое закрытие, отмена и очистка

**Действия:** два читателя одного shared package; отменить одного, затем второго. Повторить с поздним OPEN, backpressure на 15 секунд, потерей CLOSE ACK, retention/cleanup во время активного read lease, остановкой worker. Проверить upload и Drop spool при поздней физической записи после отмены.

**PASS:** отмена одного не повреждает второго; cleanup не удаляет занятые данные; DONE/STOPPED не опережает доказанное завершение физического эффекта. Неопределённое владение остаётся учтённым, после квалифицированного восстановления ресурс освобождается один раз. Нет утечки fd/handles/tasks/квоты.

### T08 — исключённые функции и действующий fallback

**Действия:** составить полный граф включения U03 streaming и нового CAS execution job: exports/imports/providers/routes/worker/DDL/capabilities/preferences. На релизной сборке проверить отсутствующую/выключенную capability, прямое обращение к неразрешённому маршруту, старый клиент, retained старые originals, restart. Через обычный UI загрузить 128 файлов owner и 128 Drop, включая 0/1 байт и границы fast path.

**PASS:** незавершённый режим недоступен по контракту и не принимает durable intent, который никто не исполнит; обычная загрузка и recovery работают с полным oracle. Fallback не ослабляет SHA/права и не скрывает ошибочный 404 поддерживаемого batch endpoint. Нет включённой миграции, требующей отсутствующего worker/executor.

Если новый streaming всё же входит в релиз, дополнительно обязательны реальные per-chunk task binding, SQL roles/predicates/concurrency, 16 подготовленных native spool cases, lost claim/ACK, process crash, physical CLOSE и browser recovery. 110 mock/component PASS этих условий не заменяют.

### T09 — чистая сборка и runtime composition

**Действия:** из отдельного checkout каждого выпускаемого commit установить pinned dependencies и собрать штатным production способом, без унаследованного dist/node_modules другого кандидата. Выполнить предписанные CI lint/typecheck/tests, затем запустить именно полученные API/worker/web и клиенты. Consumer-contract тестам дать явно закреплённые внешние revisions, если этого требует policy.

**PASS:** нет generated-config/alias расхождений, отсутствующих methods/wrapper forwarding и test-only endpoint вместо штатного пути. Readiness проверяет работающий backend и migration admission. Состав процесса, source/binary hashes и результаты сборки записаны. Разница чистого и прежнего build не маскируется копированием старого dist.

### T10 — retained recovery, checkpoint и реальный NTFS journal gap

**Вход:** отдельный собственный NTFS VHD с известным volume ID; 10000 файлов и 1024 каталога; два независимых root/profile. Рабочий журнал системного C: не сбрасывать и не переполнять специально.

**Действия:** сохранить qualified checkpoint и несколько pending originals; трижды перезапустить клиент, проверить монотонное продвижение persisted cursor. В отдельной фазе изменить hardlinks несвязанного файла вне roots; отдельно создать/изменить alias, действительно связанный с файлом внутри тестового root, сохраняя hardlink safety. Затем на собственном томе фактически вызвать потерю journal bounds/reset, подтвердить это нативными данными и восстановить оба roots. Сверить C01 с доступными историческими DB/WAL/trace; зафиксировать причину прежней задержки либо точную границу воспроизводимости.

**PASS:** checkpoint не принимается при несовпадении qualification/volume/journal/source generation; истинный gap вызывает необходимую reconciliation с полным oracle; recovery одного root не ACK-ает cursor другого. Нет циклического повторения одного retained диапазона, потери новых hints или повторных originals. Несвязанные внешние события не инициируют повторный полный root scan; связанный alias не обходит проверку источника. Ни чистка профиля, ни увеличенный timeout не являются исправлением.

Отсутствующий исторический C01 input фиксируется отдельно: новый синтетический случай не объявляется воспроизведением именно исторических 300 секунд. Для допуска текущего пути обязательны положительные native проверки описанных свойств и явный разбор оставшейся неопределённости в DEFECTS, без автоматического закрытия старого FAIL.

### 7.2. B01 — сравнение исходного и исправленного пути

1. До исправлений сохранить работоспособную исходную сборку каждого канала из материалов N01/P02/U03/D04. Точный состав, режим и ресурсы подтвердить. Падающий case даёт `INVALID_BASELINE`, не низкую «норму».
2. Закрепить корпуса:
   - Neptune: initial 4096 × 48 КиБ; fresh ADD1024, overwrite512, mixed256+256.
   - Pluto: initial512 × 48 КиБ и fresh128/overwrite128 на том же профиле.
   - Web/Drop: по 128 × 48 КиБ через реальный браузер до конечного stored.
   - Owner/shared: cold F4 и F48 по 4096 файлов; DIR-W/DIR-T по 1024.
   - Большие передачи: один файл 2 ГиБ и 8 × 256 МиБ, фактические уникальные bytes, direct и применяемый TLS/proxy маршрут.
3. На одинаковых backend/TLS/RTT/shaping/disk/cache settings выполнить **три baseline и три candidate** повтора в перемежающемся порядке A/B. Для cold download не переиспользовать готовый package. Все повторы должны пройти integrity.
4. Метрика — wall time обычной операции, включающий capture/hash/queue/publication, либо download+извлечение; генерация исходного корпуса до старта. Oracle отдельно. На сети считать уникальный payload, не retry/сжатый исходный объём.
5. **B01 PASS:** медиана candidate ≥90% baseline для каждой сравнимой строки; нет повторяемого голодания, роста ресурсов/долга или необъяснённых пауз. Опубликовать min/median/max и все samples. Отдельно хуже 80% baseline median — обязательный разбор даже при удовлетворительной общей медиане.
6. При нестабильном стенде признать конкретную попытку invalid по измеренным внешним причинам и сохранить её. Нельзя удалять медленный валидный sample. При пограничном результате один дополнительный A/B-повтор допустим; он включается в общую выборку.

Если исправление корректности даёт подтверждённую регрессию >10%, сначала искать случайную регрессию/неправильный путь. Не ослаблять correctness ради цифры. Если безопасный фикс неизбежно медленнее — представить пользователю точное изменение и затронутый сценарий; **не ослаблять 10% gate самостоятельно**.

### 7.3. B02 — совместная нагрузка

Обособленные скорости каналов нельзя требовать одновременно без учёта общих четырёх физических workers и конкуренции диска. Для совместного прогона фиксируются распределение ресурсов, суммарный throughput, latency каждого канала, очередь/долг и их восстановление.

После снятия совместной нагрузки повторить короткий фиксированный B01 cohort: скорость возвращается в 10% диапазон. Нельзя сохранять красивый fps Neptune за счёт бесконечного ожидания Drop или других клиентов.

Смена системного proxy проверяется в изолированном пользовательском/VM окружении, если это заявленный production-путь. Process-scoped proxy сам по себе не доказывает системную настройку Windows. Если такого окружения нет, этот пункт фиксируется BLOCKED и не маскируется повтором HTTP unit-теста.

Внешний VLESS из прежнего прогона не использовать: его E2E-туннель был отклонён автоматической проверкой разрешений. Собственный локальный proxy проверяет сетевое поведение без обхода этого отказа. Протокольный VLESS-specific PASS не заявляется.

### Откат

Различать:

1. **До открытия новых writers:** вернуть прежние binaries, если совместимы с уже применённой схемой; иначе восстановить согласованный checkpoint.
2. **После новых записей:** нельзя откатывать только БД или применять down.sql, теряя новые bytes/версии. Сначала закрыть writers, сохранить post-update originals/catalog/storage evidence и определить квалифицированный roll-forward либо согласованное восстановление данных.

Для каждой миграции заранее записать reversible/forward-only, совместимость старого бинарника и конкретную точку возврата. Обязательный M05 восстанавливает сервис, а не только читает tar/pg_restore list. RPO/RTO измеряются фактически; нулевую потерю при возврате к старому backup без переноса новых записей не обещать.

Подписание и системные security prompts выполняются штатным разрешённым способом. Test key или проверка отказа неподписанного MSI не заменяет положительный signed-updater E2E. Если выпускается MSI, отсутствие нужного trusted signing fixture — BLOCKED этого формата.

## 11. Финальный совместный прогон

### 11.1. Входной гейт J00

Запуск разрешён только после отдельного поручения пользователя и после:

- R01–R11 закрыты в выпускаемом составе; обязательные T/F/X/M-проверки пройдены либо для совместного исполнения уже подготовлены точные безопасные инъекции;
- B01 зафиксирован, ошибки baseline устранены;
- согласованный кандидат собран из неизменяемых source revisions, никакой участник не пересобирает используемый бинарник;
- real Windows/NTFS Neptune, native Linux/systemd Pluto, настоящий Kernel, production-built Saturn API/worker/web, реальные браузеры и используемый backend;
- изолированы аккаунты, profiles, storage roots и fault control; реальный backup всех свидетельств/критического состояния доступен;
- ресурсы посчитаны по уже квалифицированному resource-v2 без двойного вычитания занятого объёма. Учтены corpus, backend bytes, retained originals, DB/WAL, readback/ZIP/temp и аварийный запас **не менее 8 ГиБ на системном диске**. При необходимости больший запас записать заранее.

Не считать физически свободное место равным разрешённому бюджету. Не резервировать огромные корпуса только в логическом manifest. Если места недостаточно, очистить только завершённые собственные данные после подтверждения evidence; нельзя трогать чужие стенды, архивы или ранее отклонённые цели удаления.

### 11.2. Время и цикл

Сохраняется прежнее правило: **6 часов с фактического T0 допуска новых циклов**, проверка каждые **30 минут**, последний допущенный цикл доводится до завершения с необходимыми исправлениями и адресными повторами. T0/deadline неизменны, простои/ремонты входят в окно.

Это не обещание, что 500k sync и readback при нынешней скорости закончатся за 6 часов. Продолжение последнего цикла может занять дольше; прогресс и отдельные ETA publication/readback публикуются по измерениям.

Никаких новых ступеней после deadline. Для обеспечения целевого масштаба 500k-цикл допускается **в начале после smoke**, а не в последние минуты. Корпус генерируется до T0, но не presealed/не загружен в Neptune до измеряемого запуска.

### 11.3. Состав и последовательность

| ID / момент | Нагрузка и действие | Проверка |
| --- | --- | --- |
| J01 — начало | Одновременный малый smoke всех шести каналов и Kernel; по 32 файла, один share/Drop, один restart клиента | Реальные конечные SHA/IDs; маршруты/версии/credentials верны, чужие данные не затронуты |
| J02 — сразу после J01 | Neptune: **500000 уникальных реальных файлов, ≥20 ГиБ**, один новый тестовый root/profile; известное дерево, SHA-manifest, пустые каталоги | Счётчики scanned/prepared/published/readback разделены. Проверка завершения только после всех published + full readback |
| J03 — во время J02 | **20 отдельных native Pluto backup jobs**, разные source/state identities, по 1024 ×48 КиБ, общие Saturn/backend ресурсы | Реальное перекрытие всех 20 jobs не менее 60 секунд, trace PIDs/job IDs/progress; каждый завершён и прочитан. Это не требование 20 физических workers |
| J04 — одновременно | Owner upload, Drop, owner/shared download по ограниченным порциям 128 файлов; повторение порций, versions/retention, F03 mutable vault в отдельном root | Правильные receipts и versions, no copies; нет голодания каналов; steady очереди и bounded temp |

| J07 — после deadline / завершение | Новых циклов нет; завершить допущенный workload, остановить mutator, дождаться convergence, полный readback; короткий B02 recovery sample | 500000 файлов, ≥20 ГиБ, exact tree/SHA; 20 jobs PASS; все контрольные операции settled; нет неожиданных UNKNOWN/pending/debt |

Одновременный отказ всего собственного стека выполняется только после фиксации recoverable state и при доступном disk reserve. Нельзя вместе с ним выключать Docker engine/ПК или менять основной proxy пользователя.

Если J02/J03 не помещаются в фактический ресурсный бюджет, итог `BLOCKED_CAPACITY`, а не уменьшенный корпус под прежним PASS. Уменьшение этой цели возможно только отдельным решением пользователя.

### 11.4. Контроль каждые 30 минут

Проверять и записывать:

- PID + creation time + command/image, принадлежность процессов;
- timestamps и прирост **полезного** progress: новые подтверждённые публикации, продвижение scan/recovery/readback, завершённые jobs; простой heartbeat не progress;
- per-channel files/bytes, скорости по последнему окну и накопленные, attempts/retry bytes, queue depth/oldest age/UNKNOWN;
- disk свободный/зарезервированный, CPU/RAM/RSS/I/O/fd, Docker/DB health, lock waits и backend slots;
- достигнутый охват T/F/X/M/J и оставшиеся случаи;
- ETA отдельно для оставшегося sync и full readback с диапазоном и размером выборки.

Нет полезного прогресса при готовом backlog более 5 минут — диагностический FAIL до объяснения; отличать продуктивный большой scan от зависшего HTTP. Low disk или неконтролируемый рост ресурсов останавливает новые admissions, сохраняет начатые originals и evidence.

### 11.5. Исправления во время прогона

Сначала сохранить failure evidence и identities. Изолировать продукт/fixture. Не переписывать активные binaries. Сделать новый кандидат, повторить конкретный RED→GREEN и затронутые сценарии; продолжать сохранённый профиль, если совместимость это позволяет.

Исправление общего storage/DB/executor требует повторной интеграции всех затронутых каналов. Старые результаты другого candidate tuple не становятся доказательством нового. Если после исправления не осталось достаточной совместной проверки финального состава, итог текущего прогона остаётся PARTIAL; необходимый повтор указывается явно, а не заменяется суммарными шестью часами разных сборок.

### 11.6. Выходной гейт J08

- Все обязательные инварианты и достигнутые масштабы подтверждены.
- Полный readback завершён; нет необъяснённых duplicates, stale versions, неправильных aggregates и потерянных pending originals.
- Каждый запланированный fault имеет проверенный исход; неопределённое состояние не удалялось для очистки.
- Скорость изолированных B01/B02 сохранена; показатели под общей конкуренцией опубликованы отдельно.
- Созданы итоговый отчёт, список FAIL/BLOCKED/NOT_RUN и receipts.
- Остановлены только owned процессы и отключена автоматическая проверка. Evidence сохранено; удаление тестовых данных — отдельный подтверждённый этап с проверкой принадлежности.

## 12. Коммиты, release candidate и production

### 12.1. Последовательность

1. **Состав и исправления.** Зафиксировать ownership изменений четырёх репозиториев, закончить R/T и пользовательскую приёмку. Не включать весь грязный workspace одним indiscriminate commit.
2. **Локальные коммиты кандидата.** После разрешения этого этапа создать согласованные commits, проверить source manifests. Закрепить ссылки межпроектных зависимостей. Не выдавать сегодняшние подготовленные документы за уже сделанные commits.
3. **Воспроизводимая RC-сборка из этих commits.** Выполнить T09/M08 и штатные release checks; версии/tag ещё не публиковать как latest. Если подпись меняет bytes, именно подписанные assets должны пройти update/qualification.
4. **Миграции и exact-version обновление.** M00–M07 на фактических исходных prod версиях и RC. Затем совместный прогон раздела 11 на этом составе.
5. **Финальный GO review.** Заполнить раздел 13, приложить миграционный diff, backup/restore proof, результаты, release notes, фактические ограничения и план развёртывания. Это конкретный пакет для решения пользователя о production.
6. **Публикация только после разрешения.** Штатный release workflow: prerelease/staged assets, проверка полных manifests/signatures/checksums/tag → tested commit, anonymous download verification где предусмотрено, затем final qualification и promotion. Не перезаписывать опубликованные bytes.
7. **Production rollout.** По заранее проверенному порядку ниже; canary → ограниченная группа → остальная система. Контроль после каждого этапа; при FAIL не переходить дальше.

Изменение исходников, миграции, флагов, зависимости или release payload после квалификации создаёт новый кандидат и инвалидирует связанные receipts. Cosmetic docs-only изменение не подменяет binary identity; если сборка встраивает commit SHA, требуется пересборка и предусмотренная повторная квалификация.

### 12.2. Порядок обновления

Точный порядок утверждается после M03. Базовое правило — **сначала совместимый серверный контракт, затем новые клиенты**.

- Сохранить согласованный pre-update backup и возможность восстановления; проверить restore на стенде до окна production.
- Если Kernel-контракт необходим новому Saturn, сначала совместимый Kernel с успешной проверкой старых клиентов; иначе не обновлять Kernel исключительно ради изменения номера.
- При отсутствии доказанной rolling compatibility закрыть admissions и остановить writers; выполнить migration один раз; запустить согласованные Saturn API/worker, затем соответствующий web. Старый worker не должен писать в несовместимую схему.
- Поднять canary Neptune/Pluto с **тестовыми источниками** через production endpoints; проверить smoke/readback/restart, затем обновлять пользователей/daemon группами.
- После завершения проверить actual versions/digests, migration ledger, очереди, ошибки, disk/DB/backend и права.

Canary минимум: 32 новых файла, 8 overwrite, 8 rename/move, 8 разрешённых delete, 8 каталогов, один большой файл, owner/Drop/shared операции, NOOP и restart клиента. Все bytes/версии проверяются. Не инъецировать падение всего production ради smoke: fault matrix уже выполнена на стенде.

До переключения записей зафиксировать критерии остановки rollout: любое расхождение SHA/дерева/версий, ошибочное удаление, нарушение прав, необъяснённый UNKNOWN, необратимая миграционная ошибка, отсутствие полезного progress или устойчивая неприемлемая регрессия.

При аварии действовать по M05/rollback plan. Не делать слепой DB downgrade после новых пользовательских записей. Сначала защитить новые данные, сохранить evidence и остановить распространение дефекта.

### 12.3. Документация выпуска

Обновить в соответствующих проектах:

- changelog/release notes с конкретными исправлениями и реальными измерениями;
- поддерживаемые режимы, backend, ОС/архитектуры, размер файла и дерева;
- включение capabilities и поведение fallback;
- migration/upgrade/rollback и сохранность pending operations;
- MSI/portable/systemd/update/signature contract;
- known limitations и отдельно отложенные ускорения.

Не писать «все тесты пройдены», если имеются непокрытые обязательные native/UI/provider случаи. Исторические 50+ и новый локальный benchmark не выдаются за гарантированный throughput production.

## 13. Решение о допуске

1. Состав релиза известен; обязательные дефекты закрыты и подтверждены.
2. Все обязательные тесты выпускаемых функций PASS на согласованном кандидате. Отложенные новые функции действительно не поставляются и не нужны старым pending операциям.
3. B01/B02 удовлетворяют сохранению скорости либо пользователь отдельно принял измеренное исключение; нет скрытого снижения correctness.
4. Совместный прогон, масштаб и полный readback завершены; клиентские дубли не возникли.
5. Фактический upgrade, mixed-version boundaries, подписи, миграции и восстановление проверены.
6. Штатные release qualification gates не обходятся, assets совпадают с tested tuple.
7. Подготовлен конкретный rollout/rollback пакет и получено разрешение на production.

### NO_GO / BLOCKED

Любой открытый correctness/security/durability дефект; неподтверждённая миграция/rollback; отсутствие нужного signed/native/provider стенда; пропущенный обязательный readback/масштаб; скрытая активация незавершённой функции; несовпадение tested и выпускаемых bytes.

Скорость ниже прежних 50/6/100 при выполненном новом сравнительном gate **сама по себе не NO_GO**.

### Явно отложено

Дальнейшее достижение максимальных fps/Мбит/с, Rust/C# переписывание серверного стека, увеличение concurrency ради рекорда, новый SQL coalescing/parent cache и незавершённые альтернативные upload/CAS пути. Их backlog сохраняется; в этот выпуск они не добавляются без необходимости для исправления дефекта.

## 14. Организация будущего исполнения

Параллельные lanes после разрешения:

- **DB/общий Saturn:** R01/R02/R05/R08 и T01/T02/T06/T07, contracts/migrations.
- **Neptune:** R03/R04/R11, T03–T05/T10, F01–F04/F13–F15, Windows update.
- **Pluto/Kernel:** F05/F06/F16, клиентская сеть/recovery, native systemd/update.
- **Web/Drop/download:** R06, T08, F07–F12/F17, browser/fault/security.

Каждый lane имеет собственную БД/namespace и immutable сборку. Общие files/migration numbers меняются одним владельцем с проверкой передачи. Native источники по возможности размещаются на отдельных томах, чтобы чужие hardlink/USN изменения не искажали измерения.

Единый интеграционный владелец собирает exact tuple и снимает устаревшие результаты из приёмочного зачёта. Короткие независимые тесты идут параллельно; миграционные проверки общего stand и сравнения скорости — в выделенных окнах. Во время финального совместного прогона фоновые сборки/микробенчмарки не запускаются.

Ближайшее допустимое действие после отдельного разрешения на работу: подготовить RELEASE_MANIFEST/SCOPE/DEFECTS/TEST_MAP, закрепить исходные сборки и начать **T01/T02/T03**. Сейчас этот документ не запускает ни одно из этих действий.

# P02 — Pluto:50+ файлов/с,6+ каталогов/с и 100 Мбит/с

Дата: 19 октября 2026. Статус: **задание к выполнению; целевая производительность Pluto не доказана**. Владелец: агент P02. Основной репозиторий: `pluto`. Общие изменения Saturn интегрирует N01.

## Обязательная цель

Привести **реальный собранный Pluto**, работающий штатным service/indexed-sync путём с Saturn, к следующим показателям и подтвердить их на собственном стенде:

- initial upload: не менее 50 мелких файлов/с;
- повторная синхронизация после изменений: не менее 50/с отдельно для новых файлов и новых версий существующих;
- создание новых каталогов: не менее 6/с при initial, fresh и смешанном дереве;
- полезная передача больших файлов: не менее 100 Мбит/с на линии с запасом и NET-100 на ограниченном канале;
- автоматическое восстановление после отказа без потери очереди, повторных эффектов или ослабления контроля доступа.

Не завершать работу после переноса кода Neptune или успешной компиляции Go. Цель — доказанный результат Pluto. Neptune исходно показывает 51,78–52,09/с в своей локальной серии; это не baseline Pluto. Сначала измерить текущий Pluto на том же корпусе и ресурсных лимитах.

Основное направление — Pluto → Saturn/storage. Сохранить обратную синхронизацию, service lifecycle и поддержку существующих профилей. Принять одну фактически используемую целевую ОС как основную приёмочную, записав её в manifest; если Pluto развёрнут и на Windows, и на Linux, выполнить native smoke/recovery на обеих. Результат в Linux-контейнере не объявлять доказательством Windows filesystem semantics и наоборот.

## Текущее состояние, с которого начинать

Pluto уже имеет `small-batches v1`, собственные durable state/artifacts и режимы bulk/changes. В снимке 19 октября production Go-код не обращается к новому `small-jobs`, на котором измерялся полный новый путь Neptune. Через старый batch path доступна часть общих серверных улучшений `completeSmallCatalogUpload`, verified write и publication groups.

Поэтому порядок: проверить текущие capabilities и fast-path coverage → baseline → добавить недостающий клиентский контракт и pipeline → измерить → работать над оставшимся bottleneck. Не заменять существующий протокол неограниченной массовой отправкой и не импортировать C#-специфичные предположения о SQLite/NTFS в Go.

Ранее исправлялись guarded proxy/DNS, отдельный heartbeat и deadlines; их наличие не равно приёмке на текущем билде. Исторический сетевой план содержит оставшиеся вопросы — перепроверить актуальность до внесения правки.

Инженерный порог 5 с одиночной правки задаётся для отзывчивости; прежних измерений этого результата нет. Для пакетного fresh допустим контролируемый сбор порции под штатной паузой **собственной** очереди и измеряемое возобновление без reset/re-enrollment. Не создавать presealed batch заранее. Отдельный P-F-SINGLE и LONG обязаны пройти через обычные file events/polling и service scheduling без принудительного внутреннего engine call. Если файлы публиковались ещё во время генерации порции, записать counts/timestamps и включить весь соответствующий интервал; нельзя считать все 4096 по времени только последнего хвоста.

## План реализации

### P-A — baseline, профиль и штатный путь

Собрать Pluto и Saturn, стартовать отдельные service/profile/root, сделать полный initial+fresh smoke. Записать реальные poll/debounce интервалы, mode bulk/changes, capabilities, число requests/file, время local SQLite, capture/hash/spool, network control/data, server SQL/backend, physical slots.

Отдельно проверить: используется ли нужный mode обычным CLI/service, не остался ли fast path только внутри тестового API; не выполняется ли heartbeat синхронно в Loop; не зависит ли fresh retry от следующего file event или пятиминутного таймера.

### P-B — перенос долговечного execution job

Согласовать с N01 существующую серверную schema/capability. Реализовать Go encoding/decoding и передачу, сохраняя exact plan digest, individual original identities, resume offsets и bounded streamed payload. Не вводить несовместимые поля под прежней schema.

Запись immutable plan/artifact в durable state должна предшествовать первому необратимому send. После неизвестного результата читать status исходного job/member; не пересоздавать случайные operation IDs. После restart тот же план и payload доступны без повторного захвата уже изменённого исходного файла. Полностью отработать crash между записью state, sealing, admission, частичным body, publication и receipt persistence.

Ввести bounded pipeline следующего задания, согласованный с server credits. За основу — до 16 элементов/задание, максимум 2 задания в pipeline и 4 физических backend workers, если capability именно это поддерживает. Не зашивать больше объявленных server limits. Очереди, goroutines, открытые descriptors, bytes in flight и SQLite transactions должны иметь измеряемые пределы.

Разделять группы по совместимым parent/conditions, не допуская starvation редких parents. Неподходящий файл уходит на корректный fallback. Обновить retained-operation migration и downgrade поведение. Добавить fixtures совместимости wire между C#/Go/server без использования единой функции-генератора одновременно как реализации и oracle.

### P-C — повторные изменения и каталоги

Сначала проверить fresh additions тем же новым протоколом; затем отдельно ускорять overwrite с CAS. Если нужен новый server contract для existing version, подготовить запрос N01 с минимальным воспроизводителем и негативными тестами. Не выдавать generic batch envelope за доказанную экономию серверных транзакций.

Для каталогов учитывать parent dependency и уже существующие каталоги, но не подменять mkdir статистикой cache hits. Независимые sibling operations могут выполняться параллельно ограниченно; глубина дерева не должна вызывать повторный full-tree walk на каждого child. Новые directory batches сохраняют индивидуальный result и outcome lookup.

### P-D — сеть, service loop и 100 Мбит/с

Проверить размеры buffers/chunks, allocations, лишние whole-body copies, hashing CPU, io.Copy/streaming, HTTP connection reuse и TLS/proxy handshake frequency. Измерять память и goroutine/FD counts, а не только FPS.

Для control — bounded полный request+body deadline; connect/TLS отдельно; для data — idle deadline с продлением на реальные bytes и caller cancellation. Нельзя отсчитывать idle от enqueue/progress UI callback. Legacy и guarded paths не должны держать рабочие слоты несколько минут после зависшего body.

Проверить единый direct/environment/system-configured proxy policy в пределах возможностей Go-продукта, корректный CONNECT, proxy credentials и 407. DNS должен пробовать разрешённые IPv4/IPv6 candidates, сохраняя address restrictions, TLS hostname и Saturn identity; нельзя обходить SSRF защиту fallback-адресом.

Heartbeat — отдельный bounded worker, максимум один одновременно; ответ heartbeat не задерживает следующую sync attempt. Route event coalescing и probe не создают retry storm. Проверить отсутствие удаления registration token из-за ответа посредника.

## Fault/recovery матрица Pluto

- Loss after backend write, after server publication и after response before durable receipt. Новый OS process с тем же profile восстанавливает ровно прежние операции.
- Обрыв job после 5/16 элементов, повреждённый/усечённый multipart, incomplete local artifact. Неизвестные/незавершённые данные не публикуются как успешные.
- Изменить исходный файл после sealing и до restart: recovery использует зафиксированный original, следующее изменение становится отдельной версией.
- Server/DB/backend недоступен, возвращает 429/503 Retry-After; очередь сохраняется и самостоятельно продолжает после восстановления. Ресурсные счётчики возвращаются к норме.
- Headers-only stall, data idle и длинная прогрессирующая передача за пределами control deadline.
- Первый DNS IP недоступен, следующий разрешён; IPv4/IPv6 mixed, TLS mismatch, CONNECT auth407, server401/403. Токен Saturn не теряется при 407.
- Route/proxy switch в своей fixture, сетевые события пачкой, sleep/resume service event: одна актуальная probe generation; поздний старый success игнорируется.
- Heartbeat завис: service всё ещё планирует sync/recovery, нет второго параллельного heartbeat.
- Отмена пользователя не записывается как network failure; сетевой timeout не выдаётся за пользовательскую отмену.
- Конкурентный overwrite/revoke/parent rename, denied last batch member; нет повышения прав или слепого last-writer-wins.
- Upgrade/downgrade capability и открытие retained profile другим процессом: owner/lock сохраняются, двойной writer не допускается.

Для восстановления задать проверяемый срок начала прогресса <=60 с после доступности сервера и окончания действующего Retry-After; если документированный backoff длиннее, определить и обосновать иной конечный bound до серии. Бесконечное ожидание нового file event не принимается.

## Одни и те же единицы измерения во всех четырёх заданиях

### Файлы и каталоги

`files_per_second = число уникальных полностью завершённых файлов / wall_seconds`. Для upload завершение означает подтверждённую публикацию, доступность правильных байтов и долговечный результат. HTTP 200/202, число отправленных запросов, принятые в очередь элементы, переданные chunks и выданные operation IDs не равны завершённым файлам.

`directories_per_second = число новых полностью созданных каталогов / wall_seconds`. Повторный ensure уже существующего каталога, проверка parent и запись планируемого пути не увеличивают числитель. Для download определение завершения задано отдельно: восстановленное дерево получателя, а не создание каталогов на сервере.

Основной секундомер включает штатную клиентскую подготовку после старта операции, обнаружение/перечисление, чтение и hashing, очередь, HTTP, ожидания backend/БД, внутреннюю обязательную проверку байтов и публикацию/завершение. Генерация исходного тестового корпуса и его исходного manifest выполняются заранее. Запрещено заранее готовить внутренние sealed payload, originals, готовые receipts или архивы, если обычный пользовательский путь должен создавать их после старта.

Дополнительно считать активное время передачи и отдельные фазы. Независимая полная финальная SHA-сверка стенда может выполняться после основного секундомера; обязательно сохранять также `verified_total_seconds` и скорость с этой сверкой. Это не разрешает выносить обязательную продуктовую проверку целостности за измеряемую границу.

Для fresh-сценария основной старт — завершение заданной порции изменений в уже синхронизированной директории; зафиксировать также время первого изменения. Если публикации начались во время записи порции, нельзя делить все файлы на время только оставшегося хвоста: основной интервал должен охватывать их обработку целиком либо порция собирается под штатной паузой своей очереди с измеряемым возобновлением. Клиент остаётся запущенным. Основной результат включает обычное обнаружение изменений и планирование. Ручной вызов внутреннего engine не заменяет автоматический запуск. Отдельно измерять изменение → подтверждённая видимость p50/p95/max; не вычислять latency как 1/fps.

### Сеть: три независимых критерия

- **NET-CAPACITY:** на маршруте с запасом пропускной способности приложение передаёт не менее **100 000 000 полезных бит/с**, то есть **12 500 000 байт/с ≈11,92 МиБ/с**. Контрольный поток по тому же маршруту должен показывать минимум 120 Мбит/с, иначе стенд не способен доказать отсутствие потолка приложения на 100.
- **NET-100:** на изолированном маршруте, ограниченном 100 Мбит/с, контрольный поток должен достигать не менее 90 Мбит/с полезных данных. Приложение должно достигать **не менее 95% скорости контрольного потока** при одинаковых RTT, TLS, направлении, размере данных и числе соединений. Сохранять абсолютную скорость. Это критерий эффективности 100 Мбит-линии, а не переименование 85,5–95 Мбит полезных данных в 100 Мбит.
- **NET-RESILIENCE:** потеря связи/ответа, зависание тела, proxy/DNS и восстановление не вызывают потери данных, вечного занятия слотов, бесконечного re-enrollment или повторных эффектов. Прогрессирующую длинную передачу нельзя обрывать коротким общим таймаутом.

NET-CAPACITY и NET-100 обязательны оба. На физической линии 100 Мбит/с полезный HTTP payload меньше номинальной скорости из-за накладных расходов; требование 100 полезных проверяется отдельно на линии с запасом. Тест мелких файлов не заменяет сетевой: 50 ×48 КиБ дают только 19,6608 Мбит/с.

Сетевой payload считать по уникальным полезным байтам реально переданного и завершённого содержимого; retransmit/retry bytes записывать отдельно и не прибавлять к полезному числителю. Компрессию, дедупликацию и cache hits фиксировать; по распакованному размеру сжимаемого ZIP нельзя доказывать физическую загрузку линии.

Для NET-CAPACITY и NET-100 использовать не менее 2 ГиБ уникальных практически несжимаемых данных и не менее 120 секунд активной передачи в контрольном установившемся окне. Если 2 ГиБ завершились быстрее 120 секунд, повторять bounded порции с новыми именами/байтами, очищая завершённые только после сверки; не накапливать бесконтрольный набор. Сохранять скорость всей операции и активного интервала отдельно. Основной критерий 100 Мбит/с проверяется на всей завершённой полезной передаче; интервал нужен для выявления провалов.

Отдельно проверить один большой файл и несколько одновременно передаваемых больших файлов; нельзя обосновать отсутствие ограничения одиночного потока только десятками соединений. Если целевой поток требует параллелизма, показать доступную штатному пользователю настройку и результат одиночного потока; обязательный одиночный NET-CAPACITY остаётся в матрице.

## Воспроизводимые корпуса и матрица среды

Корпуса генерируются детерминированно по записанному seed. Версии и timestamps исходных/полученных объектов фиксировать до и после; не менять mtime искусственно так, чтобы клиент пропустил реальное изменение. Payload уникален между файлами и повторениями, не состоит из нулей, не схлопывается дедупликацией. SHA каждого файла, относительный путь, размер и список пустых каталогов записать в manifest. Стандартный символ KiB/КиБ означает 1024 байта; Mbps/Мбит/с — десятичные биты.

| Код | Корпус | Назначение |
|---|---|---|
| F48 | 4096 уникальных файлов по 48 КиБ в одном каталоге | Сопоставимый основной small-file gate >=50/с |
| F4 | 4096 файлов по 4 КиБ | Стоимость координации; обязательный gate >=50/с |
| F256 | 1024 файла по 256 КиБ; отдельно размеры 256 КиБ±1 и нулевой файл | Граница fast path, корректность fallback; скорость сообщить отдельно |
| DIR-W | 1024 новых пустых каталога одного существующего родителя | >=6 новых каталогов/с |
| DIR-T | 64 независимые цепочки глубиной 16, всего 1024 новых каталога | >=6/с на дереве; зависимость child от parent сохраняется |
| MIX | 4096 файлов по 48 КиБ в 512 новых каталогах, по 8 файлов в каждом | В одном wall-интервале >=50 файлов/с и >=6 каталогов/с |
| LONG | Непрерывная подача новых F48-порций не менее 10 минут при непустой очереди | Устойчивая скорость и отсутствие накопления долга |
| LARGE-ONE | Один файл не менее 2 ГиБ, несжимаемый | Сетевой предел одиночного потока |
| LARGE-MANY | 8 файлов по 256 МиБ, при необходимости следующие ограниченные порции | Сетевой предел штатной параллельной передачи |
| CATALOG | Не менее 100000 уже существующих записей, минимум 10000 каталогов, затем новые/изменённые порции | Не скрыть стоимость каталога пустым стендом |

F48, F4, DIR-W, DIR-T и MIX — обязательные измерения; F256 — обязательная проверка границ и публикация скорости, отдельный порог 50 для него не навязывается, так как на 100 Мбит-линии 256 КиБ-файлы физически ограничены сетью. Пограничные 0/1/256 КиБ±1 не подменяют F48.

Для CATALOG допустима только проверенная штатная загрузка или изолированный fixture, создающий согласованные реальные metadata и объекты с проверкой инвариантов. Способ подготовки явно записать; прямые SQL вставки с отключёнными guards и один фиктивный объект на 100000 записей запрещены. Минимум 100000 — обязательный масштаб данного этапа. Масштаб, близкий к пользовательским 927118 файлам и 86694 каталогам, исследовать далее при наличии бюджета; без него не делать утверждений о миллионе.

Профили среды:

| Профиль | Путь |
|---|---|
| P0 | Собственные client + Saturn + PostgreSQL + LocalStorageAdapter; минимальный RTT, без искусственной потери |
| P1 | Тот же путь через отдельный production-подобный reverse proxy с TLS; RTT20 мс, shaping100 Мбит/с |
| P2 | P1 с RTT50 мс, без искусственной потери |
| P3 | P1/P2 с управляемым разрывом, зависанием и 0,1% потерями; корректность и время восстановления |
| P4 | Изолированный экземпляр фактически используемого целевого backend, например SFTP, если он входит в инфраструктуру |

Основные F48/F4/MIX, directory и соответствующие fresh gates подтвердить в P0 и P1. В P2 обязательны NET-CAPACITY на маршруте без shaping, NET-100 и recovery; small-file скорость также измерить, но не выдавать измерение P0 за гарантию 50 при произвольном RTT. LONG выполнить в P1. P4 определить по текущей конфигурации без раскрытия секретов; если пользовательский путь действительно использует удалённый backend, повторить на нём F48/MIX/directory/network и fresh, где применимо. Без доступного P4 отметить соответствующую инфраструктурную приёмку незавершённой, а не заменить её loopback.

Нельзя менять рабочий Wi-Fi/VPN, системный proxy, firewall или сетевые настройки пользователя. Использовать собственный proxy, сетевое namespace/контейнер/VM и тестовый DNS. Эмуляция не объявляется испытанием физического адаптера; различие явно отразить.

## Статистическая приёмка и честная работа стенда

1. Для каждой обязательной короткой performance-строки: **пять последовательных завершённых повторов** неизменного билда, каждый достигает порога. Публиковать min/median/max, все отдельные результаты и число PASS. Не усреднять провал ниже 50 удачным быстрым повтором.
2. LONG: полная средняя скорость >=50 файлов/с; p10 неперекрывающихся 60-секундных окон с непустой очередью >=50; без растущего pending/publication/cleanup debt. Не выбирать только лучшие окна. Если нужна начальная раскрутка, записать её заранее и оставить в полной средней.
3. Каталоги: пять DIR-W и пять DIR-T, каждый >=6/с; MIX также проверяет 6/с одновременно с 50 файлов/с.
4. Для NET-CAPACITY/NET-100: по три успешных повтора каждой обязательной комбинации. Показывать полезные байты, wire bytes, elapsed, RTT, потери, соединения и контрольный baseline.
5. Для измерения эффекта изменения использовать A/B на одном корпусе, лимитах, backend, TLS и instrument settings. Предпочтительно ABBA; baseline — снимок до собственной правки, candidate — после. Это дополнение к пяти приёмочным повторам, а не замена.
6. Любая правка измеряемого кода/конфигурации после фиксации кандидата требует новой квалифицирующей серии затронутых строк. Старые доказательства не удалять.
7. По умолчанию PostgreSQL2 CPU/1 GiB и 4 физических backend-исполнителя, как в принятом Neptune baseline. Лимиты других процессов/пулов тоже записать. Повышение лимитов — отдельный опыт; нельзя незаметно заменить архитектурный выигрыш выделением ресурсов.
8. Все runs должны завершаться полным tree/path/size/SHA oracle. Для upload также индивидуальные IDs/versions/receipts; для overwrite — ожидаемая версия, отсутствие лишних версий после replay. Счётчик без oracle не может поставить PASS.
9. Не получать весь каталог между короткими порциями. Исторический overhead составлял 32,1 МиБ JSON и 2,46 с на запрос. Использовать дешёвую ограниченную телеметрию, а полноценный oracle — на фиксированных границах и в конце. Время наблюдения публиковать отдельно.
10. Mock/unit/server-only microbench полезны для диагностики; итоговые цифры получают только на реальном клиенте и собранном продукте. Не измерять `dev`/watch сервер как production build.

## Параллельная работа: владение правками и общие зависимости

Четыре агента работают параллельно; создавать их или отправлять им задания из этого документа автоматически не требуется. Чужой текущий прогон неприкосновенен. Наличие многих незакоммиченных изменений — исходное условие, а не разрешение их очищать.

| Агент | Основная область |
|---|---|
| N01 — Neptune | `neptune/**`; общий sync execution-job/folder protocol в Saturn |
| P02 — Pluto | `pluto/**`; Go transport, durable state, scheduler и свои тесты |
| U03 — web/Drop upload | `saturn/packages/drop/**`, upload-specific browser modules, `drop.controller.ts` |
| D04 — web/shared download | `saturn/packages/shares/**`, `saturn/packages/archive/**`, download-specific browser modules, `share.controller.ts`, `archive.controller.ts` |

Общие файлы имеют **одного интегрирующего владельца**:

- N01: `saturn/packages/database/**` и последовательность миграций; `packages/storage/**`; `packages/file-core/**`, включая общий `file.service.ts`; `packages/sync/**`; общие `packages/contracts/**`; sync HTTP/executors; `apps/api/src/file.controller.ts`, `app.module.ts`; `infra/production/**`.
- U03: общие `saturn/apps/web/src/app.tsx`, `api.ts`, `types.ts`, общий browser transfer glue.
- Общие manifest/lockfile/tsconfig менять только при доказанной необходимости через владельца соответствующего репозитория: Neptune=N01, Pluto=P02, Saturn=N01.

Это организационная ответственность за интеграцию, а не запрет остальным исследовать общий код. Если нужна общая правка, записать запрос в `.history/performance-2026-10-19/requests/<owner>/<requester>-<uuid>.md`: проблема, reproducer, точные файлы, предлагаемая правка, affected gates, baseline SHA. Продолжать независимую работу. Владелец либо вносит правку, либо письменно передаёт исключительное владение конкретными файлами на ограниченный этап.

Перед правкой общего файла захватить file claim в `.history/performance-2026-10-19/claims/` атомарным create-if-absent; записать owner/runId, точные пути, исходные hashes и heartbeat. Пустой/просроченный timestamp сам по себе не разрешает отнять файл: проверить владельца и получить явную передачу. Не запускать конкурентное изменение разных участков одного файла без такой передачи. Номер миграции не резервировать по принципу «увидел последний+1»: единый N01 распределяет номера и порядок, старые применённые миграции не переписываются.

Отдельный checkout/snapshot не устраняет конфликт интеграции. Общую исправленную зависимость принимать по manifest+patch+тестам, затем пересобрать собственный стенд и повторить affected gates. Не ждать общего владельца без полезной работы: можно готовить contract tests, прототип в собственном изолированном снимке и пакет для интеграции, но не выдавать неинтегрированный прототип за финальный продукт.

Перед завершением своего направления интегрирующий владелец проверяет открытые requests и фиксирует передачу оставшихся общих файлов другому действующему участнику. Передача требует явного принятия в coordination ledger; отсутствие ответа не считается согласием. Это позволяет продолжить работу остальных после выполнения личных performance gates и сохраняет единственного владельца каждого общего файла.

Не выполнять `git reset --hard`, `git clean`, общий stash, массовый checkout/revert, форматирование всего репозитория или массовое stage. Не коммитить чужие hunks; commits/push/deploy не требуются этим заданием. Перед сохранением правки повторно прочитать файл и сверить ожидаемый SHA; при изменении другим участником адаптировать минимальный patch. Свои новые файлы именовать по направлению и назначению.

## Собственный стенд из билда и бюджет ресурсов

Каждый агент использует собственные:

- frozen source snapshot, output build, runtime config и synthetic secrets;
- PostgreSQL container/DB/role, API instance, backend root и namespace/root/device identity;
- browser profile либо клиентский profile/state/SQLite/spool;
- proxy/shaper, порты, container labels, output/evidence paths.

Рекомендуемый префикс ресурсов: `perf-P02-<uuid>`. Порты выделять динамически на 127.0.0.1. Записывать PID **вместе с creation time и executable**, container ID/creation/labels, volume IDs и абсолютные пути. Не идентифицировать собственный процесс только по имени `dotnet/node/go`.

Собрать реальный release/production executable и запускать его по абсолютному пути. API — production composition и обычные migrations/guards/maintenance, web — собранные static assets; native — Release, Pluto — свой `go build`. Fixtures для отказов ставить вокруг транспорта/процесса, не вместо реального upload/download исполнителя. Прежний Vitest native receiver годится как образец oracle и отказов; финальную сетевую приёмку вести на собственном собранном API.

Снимок должен включать необходимые текущие незакоммиченные и новые исходники, а не только HEAD. Сделать manifest SHA до и после копирования/билда, убедиться, что значимые исходники не менялись во время захвата. Если менялись — повторить снимок. Не копировать production secrets, живые базы, .git, чужие runtime и гигабайты старых артефактов. Dependencies восстанавливать по зафиксированному lockfile; version/package upgrade не является частью задачи по умолчанию.

Не запускать общую `dev:up/dev:down`, общий compose project или cleanup по wildcard. Не перестраивать исполняемые файлы уже работающего теста. Сведения о компиляторах, runtime, зависимостях, migration list, SQL durability, TLS, proxy и backend включить в `build-manifest.json`.

Первоначальные 40 ГиБ больше не являются верхним пределом. Перед каждым новым выделением измерять фактическое свободное место и учитывать согласованные reservations остальных агентов. Резерв не менее 8 ГиБ остаётся неприкосновенным. Собственные лимиты изменять только с записью в coordination ledger; отмена общего лимита не увеличивает их автоматически. Обязательная очистка завершённых стендов после сохранения и проверки результатов сохраняется. Основание и точные идентификаторы сообщения: `.history/performance-2026-10-19/N01-budget-authorization-2245.json`.

Первичное распределение: до 6 ГиБ временных данных на агента, включая source/spool/backend/DB/логи/архив/распакованный download. Оставшийся запас — общий build/cache и рост WAL; ничего не скачивать или разворачивать на десятки ГиБ без пересчёта общего бюджета. Если отдельный сетевой тест требует больше 6 ГиБ, сначала получить ресурсное окно и временное перераспределение в coordination ledger. Предельное новое выделение на C: вычислять как `max(0, фактически свободно C: -8 ГиБ -сумма max(0, чужой reservation -подтверждённая занятая локальная часть))`. Подтверждённая занятая часть — свежая нижняя граница уникальных физических байтов на том же C:, а не логический размер, консервативная оценка общего потребления или удалённые данные. Использовать проверенную запись `saturn.performance.local-credit.v2` из `.history/performance-2026-10-19/local-credit/<OWNER>.json`, сроком не более 5 минут, с owner/runId, неизменившимся reservation, volumeId и SHA доказательств. Отсутствующие, устаревшие, withdrawn или неоднозначные данные дают нулевой credit: вычитается весь чужой reservation. Не учитывать повторно hardlinks/общие данные, гостевой объём VHD, Docker/shared-volume logical usage и remote SFTP; неизвестную физическую привязку исключать. Собственный консервативный расход плюс планируемый прирост должен отдельно укладываться в свой reservation. Изменения reservations, admission и публикацию/отзыв credit сериализовать через `resource-allocation.lock`; перед уменьшением/удалением/заменой credited данных сначала отзывать credit. Не отнимать lock по одному времени: проверять фактический процесс владельца. Перед стартом вновь проверять физический резерв 8 ГиБ. Эта формула устраняет двойной учёт уже занятых байтов, не создаёт свободного места и не разрешает запрещённую очистку. Перед публикацией владелец явно перечисляет неизменяемые файлы в frozen-files manifest и гарантирует отсутствие автоматической записи/очистки до отзыва; активные журналы, spool, БД и рабочие файлы без такой гарантии не учитываются. Проверенный helper и порядок применения описаны в `.history/performance-2026-10-19/resource-accounting-v2-active.md`. При достижении резерва прекращать поступление новых данных, сохранять состояние и очищать только свои завершённые fixtures после oracle. Не удалять неопределённые операции ради места.

Для больших файлов избегать одновременных лишних копий; source, spool, backend и download могут умножать объём в 3–4 раза. Планировать по фактической сумме. Не использовать sparse/нулевой payload, который даёт ложную сеть. Чужой образ контейнера можно использовать по image digest без изменения; старые контейнеры/fixtures из исторических скриптов не являются действующим ресурсом.

### Чистые окна измерений на общем хосте

Разработка, чтение и лёгкие адресные тесты выполняются параллельно. Квалифицирующие нагрузочные серии не должны конкурировать за один диск/CPU/NIC.

В `.history/performance-2026-10-19/` вести отдельные per-agent status/reservation файлы; фиксированный `measurement.lock` захватывать атомарным create-if-absent, owner и срок очередного heartbeat записывать явно. Очередность запрашивать по времени заявки; после своей конечной серии отпускать окно, чтобы один агент не удерживал хост на весь этап. Остальные в это время не запускают тяжёлые сборки, генерацию корпусов или полный readback на том же диске. Независимые физические хосты могут измеряться параллельно.

Уже существующий сторонний прогон не останавливать. Если он делает чистое измерение невозможным, записать contention и выполнить диагностический run с этим ограничением, затем дождаться подходящего окна или использовать другой уже доступный изолированный хост. Не объявлять занятый фон отсутствующим. Изоляция контейнеров ограничивает ресурсы, но не делает общий диск/NIC независимыми.

## Неприкосновенные гарантии

- Каждая мутация сохраняет исходную operation identity, idempotency key, individual result/receipt, path, SHA, size и version semantics.
- После неизвестного исхода: выяснить статус прежней операции → продолжить с подтверждённого offset/результата → допускать новые изменения. Нельзя превращать UNKNOWN в success/delete или создавать новый original только потому, что ответ потерян.
- Пакет должен быть ограничен по числу элементов, bytes, памяти и физическим слотам; backpressure действует до бесконтрольного чтения/запечатывания источников.
- Текущие ACL/root/device/binding/epoch/topology/backend fencing проверяются на требуемых границах. Недопустимы TTL-кэши полномочий, пропуск checks или «проверили родителя когда-то».
- SHA только исходного буфера не заменяет проверку реально сохранённых байтов. В download сверяются реально полученные файлы.
- Не отключать TLS verification, maintenance, fsync, synchronous_commit, SQLite durability, DB guards, recovery barriers или индивидуальный audit ради скорости.
- Конкурирующие изменения существующего файла разрешаются прежним CAS/version контрактом; ускорение не даёт права перезаписать чужую версию.
- Ошибки DNS/connect/proxy407/server401/403/TLS/user cancellation различаются; proxy407 не удаляет регистрацию Saturn. Отказ неизвестного посредника не признаётся доказанным отзывом регистрации.
- Сбой/недоступность backend не означает удаление файлов. Чужие root, path traversal, symlink/reparse escape и архивные опасные пути отклоняются.
- Не внедрять универсальный retry мутаций в reverse proxy. Повтор — по доказанному идемпотентному протоколу.
- Старые клиенты/capability fallback остаются работоспособными; rollout быстрых возможностей согласуется с серверным объявлением и сохранёнными pending operations.

## Оптимизации, которые следует брать за основу

Подтверждённая Neptune приёмка 19 октября: пять F48-подобных прогонов по 1280 файлов дали 51,78–52,09/с; два 4096 —50,68 и 54,12/с, на LocalStorageAdapter и реальном WindowsSyncService. Это ориентир на конкретном корпусе, не готовое доказательство для данного задания.

Эффективные направления:

1. **R01:** долговечное задание исполнения; один запрос вместо повторных control round trips для каждого малого действия, при сохранении индивидуальных originals/receipts.
2. **R02:** объединённая backend-запись с проверкой сохранённых байтов; устранение повторных open/stat/read, когда backend предоставляет доказуемо эквивалентную примитиву.
3. **R03:** настоящая SQL-обработка набора — registration/claim/publication и topology/resource guards; не цикл по тому же пофайловому дорогому SQL внутри одной оболочки.
4. **R05:** повторное использование точного immutable proof внутри одной защищённой транзакции. Это не межтранзакционный кэш текущих прав.
5. **R10:** ограниченный клиентский pipeline и экономия локальных durable worksets; подготовка следующего задания перекрывает исполнение предыдущего, физические слоты и bounded memory сохраняются.
6. Backend publication groups, одноразовый verified write, сокращение повторного разбора неизменяемого плана и групповые scope checks — использовать только на подходящем пути с тестами негативных границ.

Источники реализации: миграции 0092–0099 и 0101–0105, `sync-small-execution-job-executor.ts`, `catalog-upload-transfer.ts`, Neptune SmallBatch classes. **Миграция 0100/R09 group commit была исключена после отсутствия доказанного выигрыша**; не возвращать её автоматически. Redis, Bloom, pack storage, отключение durability и увеличение потоков не являются уже подтверждённым решением. Если новая гипотеза нужна, сначала профиль, затем изолированный A/B.

Для read/download переносить принцип сокращения повторной работы, bounded pipeline и set-based metadata, а не бессмысленно применять upload mutation protocol к чтению. Для web/Drop не передавать полномочия sync-device анонимному получателю.

## Журнал, доказательства и завершение

Журнал `.history/2026-10-19-P02-performance.md` обновлять **после каждого существенного действия/результата и не реже одного раза в 10 минут активной работы**. Во время долгого теста — начало, диагностические изменения, завершение и причина остановки. Не писать отчёт только задним числом.

Шаблон записи:

- точное время с timezone, runId, цель и гипотеза;
- входной gate/исходные hashes и незакоммиченные зависимости;
- точные затронутые файлы и причина правки;
- команда/working directory/build SHA/лимиты, без секретов;
- FAIL до правки, что исправлено, итог повторного теста;
- fps/dirs/s/Mbps, границы секундомера, целостность и recovery;
- состояние собственных процессов/ресурсов, следующий шаг/зависимость.

На каждый run сохранять как минимум `run.json`, `build-manifest.json`, `corpus-manifest.json`, `metrics.json`, `integrity.json`, `faults.json` при отказах, stdout/stderr, test report, профили и `resources.json`. Общий `summary.json` содержит все попытки, в том числе FAIL/INVALID/NOT_RUN, и ссылки на первичные результаты.

Рекомендуемые поля metrics: scenario, channel, profile, seed, expected/completed files и dirs, useful_bytes, wall_seconds, active_transfer_seconds, files_per_second, directories_per_second, payload_mbps, wire_bytes, observation_seconds, verification_seconds, latency p50/p95/max, interval windows, retry/recovery counts, peak memory/spool/WAL, build SHA, migration list, PASS/FAIL и объяснение. Метрика без знаменателя/корпуса/билда неприемлема.

Перед очисткой: сохранить полные результаты и воспроизводитель; завершить SHA/tree/versions oracle; архивировать существенные профили и проверить чтение/хеш архива. Затем удалить только свои завершённые source/spool/backend/DB/container/volume. На Windows проверить разрешённый абсолютный путь и принадлежность workspace/fixture; использовать один PowerShell и `Remove-Item -LiteralPath`, не передавать вычисленные пути в другой shell. Проверять container/volume IDs и отсутствие чужих пользователей. Никакого `docker system prune`, массового удаления .audit или всех временных каталогов.

В финале предоставить `ACCEPTANCE.md` своего направления: все gates с PASS/FAIL/BLOCKED и ссылками; минимум/медиану/максимум; честный baseline/candidate; применённые механизмы; факт реального restart и loss-after-commit; ограничения среды; точный diff/зависимости; список ресурсов и cleanup manifest. Deployment в production не выполнять без отдельного запроса.

В составе отчёта дать воспроизводимый runbook: команды сборки и запуска из чистого собственного снимка, необходимые runtime версии, synthetic configuration, включаемые capabilities/preferences, миграции, создание корпуса, точные команды каждого gate, получение результатов и безопасная очистка. После прочтения другой агент должен повторить измерение без устных пояснений; placeholders из этого задания в итоговом runbook заменяются реальными проверенными значениями без раскрытия секретов.

Задача считается завершённой только после полного собственного checklist, сохранения воспроизводимых доказательств и очистки своих завершённых стендов. Если один обязательный gate не достигнут, статус — **не завершено**, следующий цикл направляется на измеренный bottleneck.

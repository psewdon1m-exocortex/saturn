# Neptune / Saturn: высокопроизводительная первая и повторная синхронизация

## Назначение и порядок чтения

Документ задаёт проект изменений для связки **Neptune на Windows → Saturn → файловое хранилище**, включая существующий путь через SFTP. Он объединяет диагностику пользователя, приложенный локальный разбор Codex и проверенные публичные материалы Sync.com и других систем. Основной предмет — эффективность обработки больших деревьев, а не замена поставщика хранения.

Здесь определены **14 основных системных решений S01–S14 и 20 точечных решений T01–T20**. Для решений указаны алгоритмы, ограничения, примеры и проверяемый результат. Дополнительные разделы фиксируют общие контракты, состояния, настройки, сценарии отказов и порядок внедрения. Описанные API, команды CLI и новые сущности являются **проектируемыми**, а не утверждением об их наличии в текущем релизе.

Нормативные слова: **ОБЯЗАТЕЛЬНО** — условие приёмки; **ЗАПРЕЩЕНО** — недопустимая реализация; **ПО УМОЛЧАНИЮ** — выбранное поведение без дополнительной настройки. Экспериментальные возможности выключены до выполнения указанного критерия включения. Неизвестная возможность backend трактуется как неподдерживаемая, а не предполагается существующей.

Документ не утверждает, что исходники или работающий процесс были повторно проверены автором этого исследования. Локальные факты взяты из приложения; их привязку к конкретному production build необходимо зафиксировать на контрольной точке G0. Неизвестные производительность и возможности инфраструктуры закрываются измерениями и согласованием возможностей протокола, а не произвольным выбором разработчика.

| Термин | Точное значение в этом проекте |

| Публикация | Перевод проверенного содержимого в актуальную серверную версию с записью в каталог и журнал |
| Checkpoint | Сохранённый прогресс незавершённой операции, позволяющий безопасно продолжить её |
| Backpressure | При заполнении очереди или бюджета потребитель замедляет производителей, а не допускает бесконечное накопление |
| Tombstone | Запись о подтверждённом удалении, сохраняемая для клиентов, которые были отключены |

| Дельта дерева | Изменившиеся объекты и операции над ними |
| Блочная дельта | Изменившиеся участки содержимого одного файла |

| Карантин / история | Обратимое сохранение удалённой или заменённой версии до разрешённой очистки |

Единицы: `MB/GB` — десятичные; `KiB/MiB/GiB` — двоичные; все поля размеров API содержат **байты**. Время планировщика измеряется монотонными часами; календарное UTC используется для журналов и сроков хранения.

### 1.1. Выбранный режим продукта

Основной режим версии проекта: `upload_mirror_guarded` — локальный источник отправляет изменения на Saturn, но обнаруженная независимая серверная правка **не перезаписывается молча**. Автоматического скачивания серверных изменений в этом режиме нет. Конфликт сохраняется до отдельного разрешения.

На один серверный root назначается один `writer_device_id` Neptune. Другому устройству ЗАПРЕЩЕНО создавать второе независимое зеркало с удалениями в тот же root. Двусторонний многопользовательский sync — отдельный режим, не включаемый этой оптимизацией. Веб-интерфейс Saturn и другие разрешённые сервисы могут изменять root, но только через общее ядро публикации; их изменения участвуют в конфликтной модели.

Первая синхронизация и миграция работают без автоматического удаления неизвестных серверных объектов. Исключения, отсутствующие права, неподдерживаемые типы файлов и ошибки чтения показываются явно. Этот механизм не объявляется побайтовой резервной копией всех свойств NTFS: ACL, альтернативные потоки и активные базы требуют отдельно описанного покрытия.

### 2.2. Масштаб издержек

При условных 50 мс на последовательную служебную операцию:

```text
(560 000 + 3 250 000) × 0,050 с = 190 500 с ≈ 52,9 часа.
```

Это иллюстрация стоимости алгоритма, не прогноз фактического оставшегося времени. Подготовка каждого уникального каталога один раз вместо 3,81 млн обращений уменьшает число таких логических операций примерно в **56 раз**: `3 810 000 / 68 000 ≈ 56`. Общая синхронизация не ускорится автоматически в 56 раз: останутся запись каждого файла, сеть, проверка сохранённых данных и другие ограничения.

В приложении указано 166 млрд байтов. Это около 166 GB или 154,6 GiB; вероятно, отсюда различие с округлёнными «154 ГБ» в чате. Для расчётов и тестов использовать точное поле bytes, не сопоставлять округлённые единицы как одинаковые.

Средний размер файла не заменяет распределение. До подбора пакетирования собрать количество и сумму байтов в диапазонах `0`, `1–4 KiB`, `4–64 KiB`, `64–256 KiB`, `256 KiB–16 MiB`, `16–256 MiB`, `>256 MiB`, а также глубину дерева, максимальную ширину каталогов и число часто изменяющихся файлов.

| Что сообщает Sync.com | Что переносим в Neptune/Saturn | Граница подтверждения |

| Заявлены ускорение глубоких деревьев, ограничение роста памяти и сокращение фоновой работы [W01] | S02, S03, T20: потоковое перечисление, события, дешёвые статусы | Это заявления производителя, а не независимый benchmark |
| Поддерживается дедупликация **целых файлов** внутри аккаунта; для идентичной копии создаётся ссылка на известное содержимое [W02] | S14: переиспользование известного содержимого в разрешённой области | SFTP с обычными файлами не обязательно поддерживает такую же физическую ссылочную модель |
| Справка сообщает об отсутствии блочной дедупликации [W02] | Не обосновывать S13 ссылкой на Sync; использовать Syncthing/rsync | Из этого не выводится конкретная реализация всех видов частичного возобновления |
| Для частично переданных больших файлов поддерживается продолжение [W02], [W03] | S05 и S10: checkpoints и различение приёма/публикации | Resume не равен передаче разницы между двумя версиями |
| Возможны замедления после 300 000 файлов; указан предел 50 000 файлов в одной папке [W02] | Тестировать наш масштаб и широкие каталоги отдельно | Sync тоже не является доказательством отсутствия проблем на 395 000 файлов |

Текущая справка Sync о медленной передаче описывает проверку и шифрование до загрузки [W03], тогда как публикация 2023 года — параллельную проверку [W01]. Без привязки к ветке клиента и сценарию эти формулировки **не дают единого точного описания сегодняшнего конвейера**. Для нашего проекта выбирается явный проверяемый контракт S08; противоречие источников не замалчивается.

Объяснение Sync отказа от блочной дедупликации связано с их выбранной моделью приватности. Это не математическое доказательство несовместимости любых клиентских блоковых схем с шифрованием. Например, restic документирует собственную модель блоков, пакетов и шифрованного хранения [W19]. Но переносить её в Saturn без изменения модели доступа нельзя.

### 3.2. Что в изученных материалах Sync.com не подтверждено

Не найдены достаточные публичные сведения, чтобы утверждать использование Sync.com именно USN Journal, SQLite, Merkle-tree reconciliation, конкретного формата журналов/курсоров, размера пакетов мелких файлов, алгоритма адаптации параллелизма или конкретной схемы серверной транзакционной фиксации. Поэтому ниже эти механизмы помечаются как **наш проект**, обоснованный задачей и другими первичными источниками, а не как «внутренний алгоритм Sync».

CloudFiles и selective sync могут уменьшать объём локально материализованных данных, но не заменяют эффективную первую отправку уже существующих 395 000 локальных файлов. В этот проект не включается обязательная реализация файлов-заглушек или перенос источника в папку другого облачного клиента.

### 3.3. Другие применимые первичные источники

Syncthing документирует сохранённые индексы и обмен изменениями по поколению и sequence [W04], а также блочную модель содержимого [W05]. Microsoft Graph описывает начальную delta-выдачу, страницы и восстановление при недействительном курсоре [W10]. WebDAV Sync стандартизует токены и отчёты изменений [W11]. Dropbox разделяет upload sessions и пакетную фиксацию, чтобы снизить конкуренцию за пространство имён [W12]. Эти источники подтверждают жизнеспособность отдельных подходов, но не являются обещанием их производительности на нашем SFTP.

## 4. Целевая архитектура и обязательные инварианты

### 4.1. Разделение ответственности

```text

RootRegistry                               Sync API v1
  │                                           │
LocalScanner ─┐                               ├── Existing File Repository
USNAdapter ───┼─> LocalIndex (SQLite)          ├── Snapshot / ChangeFeed
Watcher ──────┘       │                       ├── Authorization / Root policy
                     ▼                       └── Admission / Operation Registry
               Reconciler / Planner                     │
                     │                                  ▼
               Durable DAG / Outbox ───────────> Backend Executor
                     │                                  │
               Resource Scheduler                       ├── Basic SFTP adapter
                 /             \                        └── Optional local agent
        SmallFileBatcher    LargeUpload                           │
                 \             /                                 ▼
                  Transfer + checkpoints                  Temporary content
                           │                              → stored verification
                           └── acknowledgements <────────→ publish + journal

UI / CLI ← read-only materialized status          Audit / metrics / recovery
```

Это независимые модули внутри существующих сервисов, а не требование создавать 15 новых микросервисов. Kafka не является обязательной зависимостью. На клиенте достаточно SQLite; на сервере — имеющегося PostgreSQL и постоянной очереди операций. Добавление брокера не должно предшествовать устранению повторных запросов.

### 4.2. Инварианты корректности

| ID | Инвариант |
|---|---|
| I01 | B меняется только после подтверждения конкретной версии или явного безопасного adoption совпадающего содержимого |
| I02 | Подтверждение поколения L=g не удаляет работу L>g |
| I03 | Курсор продвигается в одной транзакции с сохранением всех относящихся к нему записей/задач |
| I04 | Серверный high-water mark обозначает непрерывный опубликованный префикс, не максимальный выданный sequence |
| I05 | `UNKNOWN`, ошибка чтения и потерянные события никогда не превращаются в DELETE |
| I06 | Повтор операции с тем же ID и другим намерением отклоняется |
| I07 | Приём в буфер не отображается как окончательное сохранение файла |
| I08 | Для неизменившегося root с действительными индексами/курсорами нет пофайловых HEAD, MKCOL и чтения содержимого |
| I09 | Очереди и буферы в памяти ограничены; общий размер дерева ограничивается дисковой ёмкостью индекса, не размером массива |
| I10 | Все серверные способы изменения данных проходят через общее ядро публикации и журнал |
| I11 | Нельзя активировать быстрый достоверный remote-delta режим при необозримых записях в обход Saturn |
| I12 | Неизменный размер и mtime не являются универсальным доказательством неизменного содержимого |
| I13 | Пакет имеет результаты по элементам; ошибка одного файла не отменяет подтверждённые независимые файлы |
| I14 | Любая запись по node_id заново проверяет полномочия и принадлежность root; знание ID не является правом доступа |
| I15 | Удаления и замены обратимы в пределах настроенной истории; очистка истории — отдельное действие с аудитом |
| I16 | Сетевое ожидание не удерживает транзакцию PostgreSQL или SQLite |
| I17 | Не поддерживаемая backend гарантия durability не объявляется достигнутой |
| I18 | Обновление индекса не доказывает целостность физических байтов; для этого есть отдельная проверка |
| I19 | Новый движок не работает одновременно со старым в том же mapping |
| I20 | Протокол защищает от повторного эффекта; доставка запросов и событий допускает повторения |

### 4.3. Что остаётся неизбежным

Для неизвестного локального дерева нужен хотя бы один способ получить сведения о каждом объекте. Для нового уникального содержимого нужны чтение и передача байтов. При обычном физическом дереве backend должен создать отдельные файлы и каталоги. После потери всех журналов иногда нужен полный **локальный или серверный метаданный** обход. Эти нижние границы не оправдывают повторный сетевой обход перед каждой синхронизацией.

Быстрый обычный цикл должен стоить `O(E_local + E_remote + K)`, где E — прочитанные события, K — изменившиеся объекты. USN относится ко всему тому, поэтому `E_local` может включать изменения вне выбранного root. Формулировка «всегда строго O(1) независимо от всей активности ПК» была бы неверна.

## 5. Основные системные решения

### S01. Постоянная модель L/B/R вместо повторного выяснения состояния

**Приоритет:** P0. **Компоненты:** Neptune.Core, SQLite, серверные версии. **Основание:** [L01], строки 79–101; [W04].

**Проблема.** Хранить только «этот файл когда-то загружался» недостаточно. Без B клиент не отличает независимую серверную правку от своей новой версии; без L и поколений он может потерять изменения, возникшие во время передачи.

**Решение [D].** Для каждой локальной записи хранить отдельно наблюдаемое состояние, согласованное состояние и полученный серверный образ. У объекта сохраняются `local_entry_id`, файловая идентичность, родитель, исходное имя, тип, размер, mtime с точностью источника, `local_generation`, известный content hash, `remote_node_id`, `base_remote_version`, `base_content_hash`, состояние полноты наблюдения и `rules_version`.

Путь — производное отображение цепочки родителей, а не единственная идентичность. Переименование родителя не должно требовать переписывать абсолютный путь в каждой дочерней строке. Допустим инвалидационный кеш путей. При нескольких hard links одна физическая идентичность может соответствовать нескольким записям каталога: файловый ID не делать единственным первичным ключом local entries.

Планировщик действует по таблице:

| Состояние | Операция |
|---|---|
| L=B и R=B, область достоверна | NOOP, без открытия содержимого и сетевого запроса на файл |
| L изменился, R=B | PUT / MOVE / metadata update с ожидаемой версией из B |
| L=B, R изменился | REMOTE_DIVERGED; автоматическая перезапись выключена |
| L и R изменились | CONFLICT; сохранить обе доступные версии |
| L и R пришли к одинаковому достоверному хешу | ADOPT_EQUAL с условной проверкой текущей R; затем обновить B |
| B неизвестен, назначение отсутствует | CREATE_ONLY |
| B неизвестен, назначение существует и совпадает по хешу | ADOPT_EQUAL |
| B неизвестен, назначение отличается | INITIAL_CONFLICT, без автоматического overwrite |
| L отсутствует достоверно, R=B, объект ранее был согласован | DELETE_TO_QUARANTINE с expected=B |
| L неизвестен / каталог недоступен | BLOCKED_SCAN; никаких удалений |

Получение нового R из журнала **не означает**, что B автоматически стал равен R. Собственные события тоже сопоставляются с `operation_id`; не следует считать любое совпадение `device_id` доказательством завершения конкретной локальной операции.

**Пример.** Передаётся `report.md`, поколение 42, baseline `v8`. Пользователь создаёт поколение 43. Saturn публикует полученные байты как `v9`. Клиент устанавливает `B=(generation=42, remote=v9)`, но сохраняет `L=43` и новую работу. Следующая операция проверяет `expected=v9`.

**Приёмка.** В тесте с изменением файла во время передачи конечная очередь не пуста до сохранения поколения 43. При R=`v10`, полученном от другого редактора, запись поколения 43 не начинает использовать `v10` как baseline без разрешения конфликта. Повторный пустой цикл по 500 000 строк не вызывает 500 000 сетевых запросов.

### S02. Потоковая первая синхронизация и согласованный серверный снимок

**Приоритет:** P0 — потоковое перечисление и готовые ветви; P1 — согласованный snapshot и feed. **Компоненты:** LocalScanner, snapshot API, Planner. **Основание:** [L01], строки 26–51; [W10], [W17].

**Решение [D].** Сканер последовательно получает метаданные каталога и записывает страницы в SQLite. Очередь каталогов на обследование тоже находится в базе. Содержимое файлов на этой стадии не читается. Сканер, построение плана и передача готовых ветвей работают одновременно.

У Saturn создаётся материализованный снимок метаданных на ревизию C. В одной транзакции PostgreSQL с согласованным snapshot читается `published_seq=C` и копируются видимые строки root в постоянную таблицу snapshot entries. Транзакция заканчивается **до выдачи страниц клиенту**. Клиент часами читает копию, а не держит открытую транзакцию. Постраничный доступ — keyset по устойчивому ID/порядковому номеру снимка, не OFFSET по живому каталогу. Создание снимка — асинхронная повторяемая задача: при сбое транзакция копирования откатывается и строится новый согласованный снимок. Возобновляется чтение страниц уже готовой копии; незавершённая копия не публикуется как READY.

Для масштаба этого проекта полная SQL-материализация снимка выполняется одной ограниченной серверной задачей, с отдельным лимитом времени **создания**, не общей синхронизации. При превышении лимита возвращается SNAPSHOT_BUILD_FAILED, задача передачи уже готовых объектов не уничтожается. Это операция порядка числа метаданных, а не чтение 166 GB содержимого. Нужен бюджет диска для снимка и мониторинг длительности транзакции. Более сложное хранение всех версий индекса вместо копии для начальной реализации snapshot не требуется.

После страниц снимка клиент читает change feed начиная с C. События во время перечисления не теряются. Сервер сохраняет журнал от C пока действительна lease снимка. Частично полученный новый снимок хранится отдельным поколением индекса; старое состояние не стирается до готовности нового.

**Как начать передачу до получения всего R.** Неполная выдача не доказывает отсутствие объекта. Для уже обнаруженной локальной партии Neptune вызывает `resolve:batch`, который возвращает актуальное состояние конкретных назначений. Новые файлы пишутся с условием `absent`; существующие сначала проходят adoption или конфликтную проверку. Полученный позднее старый snapshot не должен затереть более новое R: применять строки по `last_seq` и поколению индекса.

Пустые каталоги — полноценные элементы плана. На первом проходе неизвестные серверные объекты сохраняются; удаления запрещены до завершения области и установления baseline.

**Пример.** Сканер дошёл до `project-a/src/a.cs`; `project-a/src` согласован. Файл начинает передаваться, пока сканер ещё обходит `project-b/node_modules`. Ошибка доступа в `project-c` блокирует только эту область и не отменяет уже опубликованные файлы.

**Приёмка.** Первый файл передаётся до завершения общего сканирования. Память не растёт линейно с количеством обнаруженных файлов. Остановка повторно обследует максимум незавершённые страницы/каталоги, но не повторяет весь сетевой план. Ни одно удаление не выводится из неполного снимка.

### S03. Локальные изменения: USN, адресные события и восстановление пропусков

**Приоритет:** P1, после S01/S05. **Компоненты:** Windows adapter, минимальная служба доступа к журналу, LocalIndex. **Основание:** [L01], строки 103–129; [W06], [W07], [W08], [W09].

**Решение [D].** Работает один читатель USN на том, распределяющий сведения по зарегистрированным roots. Он хранит идентичность тома, journal ID, next-read USN и состояние полноты. Перед запуском проверяются поколение и допустимый диапазон курсора; смена тома, журнал с другим ID, утрата нужного префикса или неподдерживаемый формат записи переводят root в `NEEDS_RECONCILIATION`.

События USN означают «перепроверь актуальное состояние объекта», а не безусловную команду PUT/DELETE. Записи содержат ограниченную информацию и могут объединять изменения; для незакрытого изменяемого файла сохраняется dirty-состояние до проверки стабильной версии. Нельзя считать один USN-record полной историей всех пользовательских записей [W08].

Курсор и upsert dirty entries фиксируются одной транзакцией SQLite. Позиция чтения журнала продвигается после сохранения работы, а не после окончания передачи всех файлов. Отдельно хранятся результаты выполнения операций.

**Начальный барьер:** получить J0; запустить запись событий; обследовать локальное дерево; воспроизвести журнал от J0 до J1; пометить обработанный диапазон. Изменения после J1 продолжают поступать как обычная работа. Переименование/перемещение каталога в root из внешней области требует обследовать вошедшее поддерево: один родительский USN-record не содержит перечисления всех потомков.

`FileSystemWatcher` используется как низколатентный сигнал и fallback. Его callback не выполняет сетевые операции и не блокируется на заполненной очереди передачи. Потеря буфера выставляет постоянный флаг неопределённости всей наблюдаемой области; попытка «просто увеличить буфер» не заменяет восстановления.

**Fallback без надёжного журнала.** При непрерывно работающем watcher обрабатываются адресные кандидаты. После перезапуска, переполнения или разрыва наблюдения выполняется локальная метаданная сверка. В строгом режиме сомнительные совпадения размера/mtime дополнительно проверяются по содержимому; такая проверка может быть дорогой, но не порождает HEAD на каждый файл. Она имеет сохраняемый прогресс. «Быстро признать всё неизменным по двум полям» не включено по умолчанию.

**Права.** Использовать USN только при реальной доступности API. Служба с повышенными правами отдаёт отфильтрованные события разрешённых томов по защищённому IPC и не выполняет произвольные файловые команды клиента. Весь UI повышать до администратора запрещено. При отсутствии прав включается fallback, а не скрытая неполная синхронизация.

**Пример.** Во время выключенного клиента изменено 12 файлов из 395 000. При доступном продолжении USN в работу поступают эти объекты и затронутые каталоги. На томе могут быть тысячи посторонних USN-записей; их чтение допустимо, сетевые запросы по неизменившимся объектам root — нет.

**Приёмка.** После crash между записью события и курсором оно либо уже в dirty queue, либо читается повторно. Переполнение watcher никогда не приводит к массовому удалению. Событие, пришедшее при активной синхронизации, не отбрасывается.

### S04. Серверный журнал с корректным порядком публикации

**Приоритет:** P1. **Компоненты:** Saturn file-core, PostgreSQL, Sync API. **Основание:** [L01], строки 131–147; [W04], [W10], [W11], [W12], [W13], [W14], [W15], [W16].

**Решение [D].** Все публикации — из Neptune, WebDAV, веб-интерфейса, переноса, удаления и восстановления — используют единое ядро изменения каталога. Журнал хранит `root_id`, `epoch`, `seq`, `node_id`, полное новое описание или tombstone, `operation_id`, причину и автора.

В P1 выбирается простой способ упорядочения: короткая блокировка строки `sync_root_clock` **только при фиксации метаданных**. В той же транзакции увеличивается её счётчик, обновляется каталог, создаётся change record и сохраняется результат операции. Следующий writer получает строку после commit/rollback предыдущего. При rollback увеличение обычного табличного счётчика откатывается. Это гарантирует опубликованный непрерывный префикс; доставка байтов и SFTP не держат эту блокировку.

```sql
BEGIN;
SELECT published_seq FROM sync_root_clock
 WHERE root_id = :root_id FOR UPDATE;
-- Повторно проверить expected version и готовность backend-результата.
-- Выделить последовательный диапазон из обычного табличного счётчика.
-- Обновить каталог, change records, operation result, root clock.
COMMIT;
```

Это логический эскиз транзакции; реальные таблицы основного каталога переиспользуются. Для пакетной публикации выделяется последовательный диапазон записей успешных элементов в одной короткой транзакции. Ошибки CAS отделяются до изменения соответствующего файла; недопустимый элемент не откатывает независимые уже завершённые операции.

**Почему не BIGSERIAL.** Транзакция A может получить 101 и задержаться, B — получить 102 и завершиться. Клиент, сохранивший `max=102`, пропустит последующий commit 101. PostgreSQL sequences сами по себе не обеспечивают нужный порядок и не откатывают выдачу как обычные строки [W14]. Данный проект не использует их в качестве доказательства полноты журнала.

`GET changes` возвращает упорядоченный непрерывный диапазон и `next_cursor`. На root установлен единый scope доступа: читатель feed имеет доступ ко всему этому root. Частичная фильтрация ACL в середине последовательности P1 не поддерживается; другой набор прав оформляется отдельным root/scope и поколением курсора. `epoch` меняется при полном перестроении индекса или смене области авторизации.

Журнал хранится не меньше 30 дней, либо от более старого C активного snapshot, пока действует его ограниченная lease. При нехватке квоты нельзя удалить префикс молча: заранее инвалидировать затрагиваемые курсоры/снимки и вернуть `410 CURSOR_EXPIRED`. Восстановление выполняется S12 без обнуления baseline и очереди.

**Внешние SFTP-записи.** По умолчанию root управляется Saturn эксклюзивно. Если backend изменяют в обход, быстрый режим может показывать только «индекс согласован», но не достоверное физическое соответствие. Для заявленной полной гарантии нужен локальный storage watcher/agent или обследование backend. При незадекларированной внешней записи root переводится в `BACKEND_UNCERTAIN`.

**Приёмка.** Искусственно менять порядок завершения 100 конкурентных транзакций; каждый клиент получает все публикации. Пустая страница не перечисляет файлы backend. Ни одна штатная серверная операция не обходит журнал.

### S05. Сохраняемый DAG, идемпотентность и продолжение после перезапуска

**Приоритет:** P0. **Компоненты:** Neptune operation store, Saturn operation registry. **Основание:** [L01], строки 183–199.

**Решение [D].** Координатор root строит постоянные операции и зависимости. `operation_id` создаётся и записывается **до первого сетевого запроса**. Он идентифицирует намерение: root, объект/назначение, тип операции, локальное поколение, expected version, правила и после sealing — хеш содержимого.

```text
LOCAL_PLANNED → WAIT_DEPENDENCIES → READY → SENDING
             → RECEIVED → BACKEND_WRITING → STORED_VERIFIED
             → PUBLISH_PENDING → PUBLISHED → CLIENT_ACKED
```

Для больших файлов это схема зависимостей **завершения**, а не запрет перекрытия передачи с записью backend. В хранилище состояния раздельно вести `receive_phase`, `backend_phase`, `publish_phase` и счётчики принятых/записанных/проверенных байтов. Backend может писать уже подтверждённые части, пока остальные ещё поступают; ждать полного RECEIVED перед первой backend-записью запрещено, иначе rolling ingress для файла больше буфера работать не будет. Общий `state` ответа — отображаемая сводка этих полей; код возобновления использует конкретные фазы и checkpoints, а не сравнение порядковых номеров строковых статусов. STORED_VERIFIED всей операции требует sealing и проверки **всего файла**, а не только полученного префикса.

`RECEIVED` и следующие серверные этапы — не обязательные отдельные сетевые round trips: сервер может объединять их в одном ответе или выдаче статусов. Побочные состояния: `RETRY_WAIT`, `SOURCE_BUSY`, `CONFLICT`, `BLOCKED_PERMISSION`, `BLOCKED_QUOTA`, `CANCEL_REQUESTED`, `SUPERSEDED`.

Координатор один на root, но исполнителей операций несколько. Любая зависимость указывает устойчивый ID, а не in-memory Task. Рабочая lease нужна для возврата незавершённых локальных задач после смерти процесса; повторный сетевой эффект предотвращает серверная идемпотентность. По истечении локальной lease сначала выясняется серверный результат.

На сервере повтор `(root_id, operation_id)` с тем же intent fingerprint возвращает существующее состояние; другое намерение получает `409 OPERATION_ID_REUSED`. Потеря ответа после публикации не вызывает повторную передачу. Клиент запрашивает результаты пачкой; успешный ответ обновляет B и подтверждённое поколение одной SQLite-транзакцией.

**Не обещать exactly-once доставку.** Запросы могут повторяться, события тоже. Проект обеспечивает отсутствие второго эффекта подтверждённой операции в действующем поколении протокола. Компактные финальные квитанции хранятся на сервере на протяжении жизни root/epoch; тяжёлые диагностические данные можно удалять по TTL. Удаление root делает старые IDs недействительными, а не позволяет выполнить их заново в другом root.

У незавершённого большого файла checkpoint включает upload ID, список подтверждённых частей, размеры, хеши и идентичность версии источника. Совпадения размера/mtime недостаточно для повторного использования старых частей после неопределённого разрыва наблюдения: нужна непрерывность журнала/неизменяемый снимок либо повторная проверка префикса.

**Пример.** Из 500 файлов пакета 490 опубликованы, 6 приняты, 4 не дошли. После перезапуска выполняется один batch status. Первые 490 не передаются; 6 продолжают серверные стадии; передаются только 4 отсутствующих элемента. У обновлённого локального файла создаётся другое поколение/операция.

**Приёмка.** Crash на каждом переходе сохраняет либо выполненный результат, либо возможность безопасного повтора. Ошибка одной ветки не возвращает весь root в начало. Завершённые каталоги остаются подтверждёнными после перезапуска.

### S06. Пакетные метаданные, адресация по ID и переиспользование существующего индекса Saturn

**Приоритет:** P0. **Компоненты:** WebDAV adapter, Saturn repository, Sync API. **Основание:** [L01], строки 11–14, 35–49.

**Решение [D].** Исправить разрешение WebDAV-пути на существующий прямой repository lookup `(parent_id, name)` вместо чтения страниц каталога. Индекс уже заявлен в локальном разборе; G0 подтверждает его DDL и фактический query plan. Новый sync API не должен снова разрешать все компоненты строкового пути для каждого файла: после регистрации root используются `node_id` и `parent_id`.

Добавляются `resolve:batch` и `directories:ensure`. Одна партия содержит до 500 элементов и до 4 MiB распакованных метаданных; первое достигнутое ограничение закрывает партию. Родитель может быть существующим node ID или временным ID из той же партии. Сервер проверяет DAG, разрешает родителей перед детьми и возвращает результат на каждый элемент.

Каталог имеет единственную логическую операцию подготовки в пределах `(root_id, epoch, local_directory_id)`. Зависимые файлы ждут её. Серверное уникальное ограничение на имя в родителе предотвращает дубликаты при гонке. Если объект уже существует, нужно проверить **тип и scope**; файл с таким именем не считается успешно подготовленным каталогом.

Состояние подтверждённого родителя сохраняется. При server change/delete/move кеш инвалидируется адресно. Ошибка `PARENT_NOT_FOUND` вызывает одну объединённую проверку соответствующей ветки, не возврат к глобальной подготовке дерева.

**Пример.** Для `a/b/c` и 1000 файлов внутри старый код многократно вызывает MKCOL для `a`, `a/b`, `a/b/c`. Новый план создаёт три уникальные задачи; пакет возвращает три node ID, после чего файлы используют ID `c`. Если все каталоги уже существуют, физических mkdir может не быть вовсе.

**Ограничение.** На чистом backend 68 000 отсутствующих каталогов всё ещё требуют 68 000 физических созданий. Пакетирование сокращает round trips и повторные проверки, а не физическую необходимость. Нельзя скрыть 1000 последовательных перечислений родителей внутри одного нового HTTP-запроса и назвать это оптимизацией.

**Приёмка.** На чистом неизменяющемся тестовом дереве каждый каталог физически создаётся не более одного успешного раза; повторы допускаются только при инъекции неопределённых сетевых исходов. В обычном sync API нет WebDAV MKCOL/HEAD на файл. Lookup широкого каталога не содержит последовательного чтения всех его страниц.

### S07. Пакеты мелких файлов с результатами на каждый элемент

**Приоритет:** P2, после S05/S10. **Компоненты:** SmallFileBatcher, ingress, backend executor. **Основание:** [L01], строки 53–75; полезная аналогия разделения приёма/фиксации — [W12].

**Решение [D].** Файлы до 256 KiB направляются в транспортные пакеты: максимум 500 файлов, максимум 32 MiB полезных байтов. Пакет закрывается также по возрасту: 1000 мс для массовой первой загрузки, 250 мс для адресных пользовательских изменений. Это не глобальный архив root.

Для P2 выбирается однозначный безопасный формат подготовки: batcher кратковременно получает защищённый от записи источник каждого малого файла, читает его **один раз** в ограниченный локальный spool, одновременно вычисляет SHA-256, затем освобождает источник. Spool содержит неизменяемые bytes и таблицу offsets; файл spool сохраняется до подтверждения/отмены всех элементов. Подготовка не держит сотни открытых исходных файлов. Локальная дополнительная запись и чтение spool — сознательная цена сокращения сетевых ожиданий; эффективность проверяется benchmark, а не предполагается для любого носителя.

По HTTP передаётся `multipart/related`: JSON-manifest, затем отдельные binary parts. Для каждого элемента заданы operation ID, source generation, размер, SHA-256 и условие назначения. Бинарные части читаются потоково; ни Neptune, ни Saturn не собирают 32 MiB × число пакетов в неограниченной памяти. Детальный контракт — раздел 7.

Saturn валидирует manifest до выделения файлов, резервирует бюджет и принимает элементы во временное состояние. Каждый полностью принятый и проверенный элемент может продвигаться независимо. Оборванная binary part не считается принятой. После разрыва клиент получает batch status и пересылает лишь необходимые элементы в новом транспортном пакете с прежними operation IDs.

Приём байтов и публикация отделены. Публикации готовых файлов группируются короткими партиями до 100 элементов/50 мс ожидания, но не удерживают namespace/SQL-блокировки во время передачи. Все успешные элементы получают собственные версии и квитанции.

**Пример.** 10 000 файлов по 16 KiB занимают около 156 MiB. При лимите 500 получается 20 транспортных пакетов вместо 10 000 индивидуальных upload-request процедур, плюс ограниченное число запросов планирования/результатов. Это не обещает 500-кратного общего ускорения: backend всё ещё открывает и сохраняет 10 000 файлов.

**Отказы.** Один конфликт не откатывает остальные файлы; неподдерживаемое имя исключается с адресной ошибкой; недостаток spool-квоты останавливает новые пакеты, не удаляет уже принятые. Финальные SHA-256 и длины проверяются независимо на стороне сервера.

**Приёмка.** В одинаковых условиях сравнить файлы/с и CPU с individual upload; при увеличении полезной пропускной способности менее чем на 15% либо росте p95 пользовательской задержки свыше 20% пакетирование для данного класса носителя не включать автоматически. Формат и корректность должны проходить тесты независимо от результата performance gate.

### S08. Хеширование в конвейере и проверка именно переданной версии

**Приоритет:** P0 для устранения повторного чтения; P2 для общего унифицированного конвейера. **Основание:** [L01], строки 16, 77; [W01], [W24].

**Решение [D].** Разделить три задачи: доказательство стабильности источника, хеш передаваемого потока и проверку физически сохранённых байтов. Они связаны, но не взаимозаменяемы.

Для нового большого уникального файла не нужен полный предварительный SHA-256 до начала передачи. Источник читается один раз, данные попадают в ограниченный chunk buffer, одновременно обновляются chunk hash и общий SHA-256. После вычисления хеша части она отправляется; общий хеш передаётся при sealing всей загрузки. Для мелких файлов хеш считается при подготовке immutable spool S07. Если протокол старого клиента обязательно требует хеш заранее, сначала выпустить совместимое расширение, а не удалять поле проверки из старого протокола.

По умолчанию источник открывается обычным Windows-чтением с разрешением других читателей и удаления/переименования (`FileShare.Read | FileShare.Delete`), но без разрешения конкурентной обычной записи в тот же файловый объект. Это позволяет сохранить открытое старое содержимое при атомарной замене пути редактором. Существующий несовместимый writer вызывает `SOURCE_BUSY` и повтор позже. Перед открытием и по открытому handle проверяется файловая идентичность, не только строка пути. Семантика sharing описана Microsoft [W24].

Это контракт для обычных стабильных файлов, **не универсальный снимок активной базы, memory-mapped хранилища или группы файлов приложения**. Такие источники требуют T17: application-consistent export или VSS с подходящей гарантией. По умолчанию нельзя объявлять их согласованными лишь после двух `stat`. Пользователь должен видеть класс гарантии; отсутствие подходящего снимка даёт адресное blocked-состояние, не молчаливую отправку потенциально смешанных байтов.

Для продолжительной передачи обычный in-place writer может столкнуться с sharing violation; это известное следствие строгого захвата версии. Для часто редактируемых больших файлов используется snapshot/spool-профиль T17 либо синхронизация откладывается. Автоматическую запись редактора не следует бесконечно блокировать неограниченными повторными захватами.

На завершении сравниваются переданная идентичность/поколение и актуальное L. Изменившийся путь, новая файловая идентичность или более свежее поколение остаются в очереди. B описывает реально переданные bytes. Часы разных ПК не участвуют в установлении порядка версий.

**Что не удаляем.** Текущая проверка Saturn путём повторного чтения backend-файла сохраняется для Basic SFTP. Подсчёт хеша на входе доказывает только корректность приёма. Перенос проверки ближе к диску допустим через S10 с явно объявленной гарантией, а не через подмену `verified=true`.

**Пример.** Для нового файла 8 GiB старый путь «хеш → хеш → передача» может трижды прочитать источник. Новый обычный путь читает исходные bytes один раз в конвейере; backend readback остаётся отдельным обязательным этапом. В режиме блочной дельты дополнительное чтение части источника допустимо и учитывается отдельно.

**Приёмка.** На стабильном новом большом файле без resume/delta исходный диск читает объём около размера файла, а не три размера. Повреждённый ingress, повреждённый временный backend-файл и изменение источника проверяются тремя разными тестами. Ни один из них не завершается ложным подтверждением.

### S09. Адаптивный планировщик с независимыми ресурсными бюджетами

**Приоритет:** P0 — фиксированные пределы; P2 — адаптация. **Основание:** [L01], строки 166–181; [W20], [W21], [W23].

**Решение [D].** Использовать отдельные бюджеты для операций метаданных, активных передач, чтения/хеширования, буферов, открытых файлов, backend-запросов, ingress-диска и лимита сетевой скорости. Все mappings одного клиента разделяют клиентский бюджет; все клиенты Saturn — бюджет одного backend. Нельзя умножать лимит на число папок или число запросов внутри файла.

Старт: 4 активных передачи, из них не более 2 больших; 8 metadata requests; 1 reader для HDD или неизвестного типа носителя, 2 для подтверждённого SSD; 64 MiB управляемых data buffers; 4 backend-потока операций в отдельном storage pool. Параметры не являются утверждением об оптимуме данного сервера.

Новые адресные изменения имеют отдельную очередь. Планировщик распределяет сервис между metadata dependencies, текущими пользовательскими изменениями, bootstrap и recovery. Сначала соблюдаются зависимости и доступность ресурсов, затем справедливость. Нельзя держать занятый upload-slot, часами ожидая ещё не созданного родителя. Нельзя держать десятки открытых файлов, ожидая network token.

**Адаптация:** каждые 30 секунд при ненулевой очереди оценивать throughput, p95 времени фиксации, ошибки, backend pool wait и потребление буферов. При запасе и улучшении разрешается +1 upload worker до 8. Пробный шаг сравнивается с предыдущим сопоставимым окном; рост throughput <5% в двух окнах откатывает шаг. `429/503`, превышение p95 более чем вдвое относительно стабильного окна или насыщенный backend queue уменьшают лимит вдвое, минимум до 1. Новый рост запрещён 60 секунд. Размеры файлов и активный режим учитываются при сравнении: окно с одним большим видео не сравнивается по files/s с тысячей пустых файлов.

В P0 эта логика выключена, используются фиксированные пределы. Автоадаптация не меняет лимиты durability, размер допустимой записи, политики удаления или проверки хешей. CPU pressure лишь снижает параллельность, а не выключает проверки.

**Пример.** Два ПК начинают bootstrap одновременно. Saturn не разрешает каждому занять по 8 SFTP-соединений: общий лимит остаётся 4 storage workers; новые изменения маленьких документов получают долю сервиса даже при больших очередях.

**Приёмка.** Количество операций и память никогда не превышают суммарные бюджеты. Рост worker count при искусственном bottleneck не вызывает линейного роста RAM/времени блокировок. Скорость сравнивается по `published files/s`, а не принятым в буфер bytes/s.

### S10. Раздельные приём, запись, верификация и безопасная публикация на backend

**Приоритет:** P0 — восстановление и честные статусы; P2 — ускоренный storage path. **Основание:** [L01], строки 73–77; [W12], [W23], [W25].

**Решение [D].** Ввести общий backend executor с постоянным intent журналом. Содержимое сначала пишется в уникальное временное назначение вида `internal/root_id/operation_id/content.tmp`. Пользовательский окончательный путь определяется по ID непосредственно перед публикацией. Временные области и история не входят в пользовательский root и защищены от произвольного доступа.

Порядок для замены файла:

1. Зарегистрировать intent и expected=B, зарезервировать место и временную область.
2. Принять/передать байты в backend temp без долгой namespace-блокировки.
3. Проверить длину и SHA-256 сохранённых bytes. При наличии соответствующей capability выполнить flush; записать фактический уровень гарантии.
4. Взять краткую логическую защиту объекта/назначения, вновь проверить expected, подготовить запись восстановления.
5. Сохранить предыдущую версию в истории; переместить готовый temp в окончательное назначение. Никакого inplace обновления единственной старой копии.
6. В короткой PostgreSQL-транзакции опубликовать новую версию, change record и финальный результат операции.
7. После commit отдать квитанцию. Сборка мусора работает отдельно.

Файловая операция и PostgreSQL-транзакция **не являются общей атомарной транзакцией**. Поэтому intent хранит пути temp/history/final, ожидаемый старый и новый хеши, стадию и результаты. При crash между шагами 5 и 6 recovery проверяет фактические объекты, завершает каталог либо восстанавливает старую версию. Неопределённая сторонняя правка даёт `BACKEND_UNCERTAIN`, а не автоматический overwrite.

Во время короткой физической публикации через Saturn чтение затронутого объекта ждёт или получает retriable `PUBLISH_IN_PROGRESS`, чтобы новый физический файл не выдавался со старой каталожной версией. При сохранении старого файла отдельным rename и последующем rename нового возможен короткий промежуток отсутствия пути **на самом backend**; он скрыт от клиентов Saturn, но не от прямого SFTP-доступа. Полную внешнюю атомарность в этом режиме не обещать. Если backend предоставляет более сильную атомарную замену, использовать её через capability.

#### Три класса возможностей backend

| Режим | Проверка | Публикуемая гарантия | Доступные ускорения |
|---|---|---|---|
| Basic SFTP | Обязательный readback temp с SHA-256; обязательный контроль длины | `verified_readback`; fsync и устойчивость namespace не подразумеваются | Пулы, pipelining, ID lookup, пакеты первого участка |
| SFTP с проверенными расширениями | Readback плюс доступные подтверждённые flush/copy/rename возможности | Отдельные признаки `file_flush_confirmed`, `namespace_durable`; не объединять их произвольно | Копирование на сервере и эффективные file transfers при реальной поддержке |
| Storage agent возле диска | Локальная верификация сохранённых bytes, flush файла и нужных каталогов по контракту ОС | `durable_namespace`, если весь контракт выполнен | Локальная раскладка пакетов, блочная сборка, hashes без передачи readback по WAN |

OpenSSH документирует pipelining, `fsync@openssh.com` и `copy-data`, но это не подтверждение наличия расширений у конкретного хранилища [W23], [W25]. `fsync` файла сам по себе не подтверждает flush каталога после rename. По умолчанию P0 сохраняет минимум `verified_readback`, соответствующий смыслу нынешней проверки. Режим `require_durable_namespace=true` требует capability; иначе root блокируется с объяснением, а не понижает гарантию молча.

**Точный контракт namespace guard.** Все штатные изменения каталога, включая metadata-only и веб-интерфейс, проходят через один namespace coordinator активного backend executor. Публикация файла запрашивает shared-защиту цепочки предков и exclusive-защиту самого node и имени назначения `(parent_id, name_key)`. Перенос/удаление каталога запрашивает exclusive-защиту его node; она несовместима с shared-защитой этого предка у потомков. Поэтому передачи в независимые temp продолжаются, но публикация внутри перемещаемой ветки ждёт. Координатор выдаёт весь набор защит атомарно либо ставит запрос в очередь; держать половину набора в ожидании второй половины запрещено. Это предотвращает взаимную блокировку при встречных переносах.

Цепочка и права повторно проверяются после выдачи защит. Между финальной проверкой expected, физической заменой и SQL commit защиты не освобождаются; ни один параллельный путь ядра не меняет защищённые версии. Блокировка строки root clock добавляется только на коротком SQL-этапе. При commit failure операция остаётся uncertain под восстановительной блокировкой; её нельзя просто повторить как новый upload. Эти локальные защиты корректны лишь при указанном ниже единственном backend-writer процессе; они не заменяют распределённый fencing.

**SFTP и конкурентные исполнители.** В P0/P1 один активный backend-writer процесс на backend; все пути записи Saturn направлены к нему. Нельзя реализовывать failover только истечением SQL lease: обычный SFTP не умеет запретить старому writer продолжить I/O по fencing token. Новый writer запускается только после подтверждённого прекращения старого процесса/соединений и разбора uncertain operations. Active-active разрешается только с backend/agent, реально проверяющим fencing, и отдельным тестом split-brain.

**Пример.** Saturn успел отправить 50 GiB в temp, но потерял HTTP-ответ. Клиент видит RECEIVED/BACKEND_WRITING и продолжает узнавать результат; не отправляет всё заново. Успешное сохранение в локальный ingress на VPS не превращает статус в «защищён на конечном диске».

**Приёмка.** Crash до/после физического rename, до/после SQL commit и потеря ответа не теряют старую версию. На Basic SFTP не исчезает контрольный readback ради более красивой скорости. Метрики отдельно измеряют оба сетевых участка и физическую фиксацию.

### S11. Идентичность, переносы, условные изменения и безопасные удаления

**Приоритет:** P1. **Основание:** [L01], строки 81–101; HTTP conditional semantics [W26].

**Решение [D].** Планировать MOVE по устойчивой идентичности, а не как DELETE+PUT содержимого. Серверный node ID сохраняется при переносе внутри root; меняются parent/name/version. У потомков не меняются content versions только из-за пути предка. Для непосредственного состава каталога хранится `children_revision`; это не сводная версия всех байтов поддерева. В P1 безопасное удаление реализуется per-node postorder и CAS каждого объекта, как в разделе 7.10. Глобальная subtree generation для ускоренного удаления — отдельная capability, не требование обновлять всех предков при каждой записи файла.

Перед namespace-операцией проверяются current expected version объекта, конфликт имени в целевом родителе, права, отсутствие цикла и принадлежность одному root. Перенос между roots по умолчанию запрещён как единый MOVE; явная операция copy+verify+retire не входит в автоматический P1. Case-only rename выполняется через безопасное временное имя, если этого требует backend, с intent и recovery.

Операции публикации содержимого под перемещаемым каталогом не используют устаревший абсолютный путь. Staging адресуется по operation ID; commit заново разрешает parent ID. На время физического rename поддерева его публикации временно закрываются namespace guard; чтение/передача в независимые temp продолжаются. После переноса они публикуются по новому пути. Нельзя держать весь root заблокированным на время загрузки 20 GiB файла.

**Удаления.** Удалять можно только ранее согласованный объект с достоверным локальным tombstone/полной соответствующей областью и `expected=B`. По умолчанию это move в историю, не физический erase. Directory delete в P1 допускается только после условного удаления согласованных детей и проверки, что каталог действительно пуст. Неожиданный серверный потомок блокирует удаление родителя; изменение согласованного ребёнка отклоняется его собственным CAS. Одна пользовательская команда удаления ветки разворачивается в сохраняемый postorder-план, а не в безусловный рекурсивный erase. Ускорение по единой subtree revision выключено до отдельного контракта и capability.

Массовое удаление требует подтверждения при `count >= 100` **или** `count / previously_managed_count >= 5%` в одном плановом окне; для маленьких корней порог отношения включается только при `count >= 10`. Число ранее согласованных объектов берётся до применения удалений. Однократное подтверждение привязано к hash плана, root и сроку 15 минут; изменённый план требует нового подтверждения.

**Пример.** Папка с 20 000 неизменённых файлов переименована. Система передаёт MOVE и необходимые метаданные, а не bytes этих файлов. Если другой сервис добавил в неё новый документ, последующая попытка удалить ветку не стирает его по старому плану.

**Приёмка.** Rename большого дерева не увеличивает `uploaded_content_bytes`; 412/409 не лечится свежим HEAD с безусловным повтором overwrite. При отключении локального диска нет серверных DELETE. История позволяет восстановить удалённый объект с новой версией и событием журнала.

### S12. Возобновляемая сверка, дерево хешей и отдельная проверка содержимого

**Приоритет:** P0 — убрать общий непреодолимый лимит; P1 — снимки и восстановление; P3 — Merkle. **Основание:** [L01], строки 22, 51, 164; [W10], [W11].

**Решение [D].** Обычная синхронизация завершается по квитанциям операций и обработанному диапазону изменений, а не обязательным повторным PROPFIND всего root. Для восстановления предусмотрен отдельный workflow с собственными курсорами, бюджетами и признаком полноты каждого поддерева.

По истечении remote cursor создаётся новый снимок S02. Он загружается в shadow-generation индекса, затем применяются изменения после cut. B и незавершённые операции сохраняются; отсутствие строки в ещё неполном новом индексе не означает удаление. После полной загрузки и replay новое R атомарно становится активным. При смене server epoch старые version tokens считаются неприменимыми; совпадающие объекты можно снова принять по проверенному содержимому, но не переносить CAS-версию между эпохами.

Временная legacy-реализация без Sync API перечисляет удалённые каталоги по постоянной очереди и сохраняет посещённые области. Если конкретный PROPFIND одного широкого каталога не имеет пагинации, это ограничение нельзя исправить только клиентским OFFSET: нужен server index API. Такой fallback не включается как якобы масштабируемое финальное решение. Усечение ответа не является успешным завершением каталога.

**Merkle как дополнительный механизм восстановления.** Хранить сводные хеши описаний поддеревьев. Для широких каталогов использовать фиксированное хеш-разбиение идентификаторов children на 256 корзин с рекурсивным разбиением переполненной корзины, а не сдвигаемые страницы по OFFSET. Хеш считается над каноническими метаданными, включая ID, parent/name, type, content hash и deletion state; в обоих сравниваемых индексах формат и epoch одинаковы. Изменение листа обновляет только затронутые корзины и предков. Сравнение выполняется на согласованном cut и только когда все dirty summaries до этого cut рассчитаны.

Сначала сравниваются summary, затем раскрываются отличающиеся ветви. Если хеш неизвестен, ветвь раскрывается; «не посчитан» не приравнивается к совпадению. Весь этот механизм относится к **индексу**, не проверяет реальное состояние диска, если индекс устарел из-за внешних записей.

**Scrub.** Фоновая задача читает физические bytes по сохранённым ожидаемым хешам, с курсором и отдельным I/O budget. По умолчанию каждый поддерживаемый объект должен попадать в план scrub за 30 суток; если бюджет не позволяет выполнить план, интерфейс показывает отставание, а не ложную дату «проверено». Изменение/удаление файла во время scrub учитывается по версии. Обычные новые изменения имеют более высокий приоритет.

**Пример.** Курсор сервера просрочен после 45 дней отсутствия ПК. Получается новый метаданный snapshot; 394 900 совпавших файлов не перезагружаются. Изменившиеся 100 объектов перепланируются по B/L/R. При неизвестных хешах требуется адресная проверка, не автоматическое принятие совпадающих mtime.

**Приёмка.** 500 000 объектов, перезапуск после каждой страницы и изменения во время выдачи приводят к полному индексу без пропусков. 100 000 — не предел root. Совпадение Merkle не скрывает специально испорченный физический файл от отдельного scrub.

### S13. Блочная дельта больших файлов по экономически оправданному пути

**Приоритет:** P3, выключено по умолчанию. **Основание:** [L01], строки 149–164; [W05], [W18].

**Решение [D].** Сначала внедрить дельту дерева. Блочная дельта включается только для файлов от 256 MiB при наличии неизменяемой базовой версии и backend, способного повторно использовать блоки **без скачивания старого файла к Neptune**. В первой реализации фиксированные блоки по 1 MiB, последний короче; все блоки и целый файл имеют SHA-256. FastCDC — отдельный последующий wire version, не обязательная незавершённая часть P3 [W18].

Процесс: получить lease базовой версии; получить её сохранённый block manifest страницами; прочитать стабильную новую версию и вычислить новый manifest; определить совпадающие и отсутствующие блоки; оценить выигрыш; передать недостающие; собрать **новый temp**, проверить целый результат и выполнить обычную CAS-публикацию. Базовую версию запрещено изменять inplace. GC не удаляет блоки/старую версию при действующей upload lease.

Выбранное правило включения: отсутствует не более 25% байтов, описания+передача+сборка прогнозируются минимум на 20% быстрее whole-file пути, есть пространство для новой версии и история старой не нарушается. Модель использует последние измеренные скорости чтения/сборки и сети; без измерений выбирается whole-file. Стоимость подготовки manifest включается в сравнение, а не скрывается.

На Basic SFTP блочная дельта по умолчанию выключена. Возможное чтение совпадающих блоков через Saturn с последующей записью обратно может сохранить клиентский WAN-трафик, но ухудшить второй участок; это не включается без отдельного benchmark. Поддерживаемый local agent либо подтверждённый backend copy-range позволяет избежать этого эффекта.

**Пример.** У 4 GiB файла изменены 8 блоков по 1 MiB без сдвига остального содержимого. Между Neptune и Saturn передаётся около 8 MiB плюс manifest вместо 4 GiB. Клиент всё равно может прочитать 4 GiB для обнаружения блоков, а backend — прочитать/собрать значительную часть файла. Вставка в начало при фиксированных блоках может разрушить совпадения: whole-file fallback обязателен.

Отдельно различать chunking для resume (например, транспортные части 8 MiB) и блоки для delta (1 MiB). Они имеют разные назначения и не обязаны совпадать.

**Приёмка.** Изменение 8 MiB в 4 GiB тестовом файле не передаёт весь файл по клиентскому участку, если capability включена. Результирующий SHA-256 равен источнику. При poor-match, отсутствии lease или дорогой сборке автоматически выбирается whole-file, без бесконечных повторных вычислений manifest.

### S14. Дедупликация целых файлов и серверное переиспользование содержимого

**Приоритет:** P2 для известных хешей; P3 для расширения каталога содержимого. **Основание:** file-level механизм Sync.com [W02]; ограничения SFTP [W23].

**Решение [D].** Для уже известного достоверного SHA-256 сделать batch lookup по `(authorization_scope, size, sha256)` и операцию `clone-content` в новый node. Ссылку на источник выдаёт сервер только в пределах разрешённой области. Знание чужого хеша не даёт права читать или ссылаться на содержимое; глобального публичного oracle «существует ли такой файл» нет.

В P2 используются достоверные хеши, уже полученные при синхронизации, чтении для spool или проверенном обнаружении локального перемещения/копии. Запрещено добавлять полный предварительный hash каждого нового большого уникального файла лишь ради почти всегда отрицательного dedup lookup. Для неизвестных новых больших файлов default — S08 streaming upload. Хеш метаданных не заменяет content hash.

Для backend с объектными неизменяемыми blobs возможна новая логическая ссылка на существующий blob. Для нынешнего native-tree/SFTP формата выбирается реальное серверное копирование при capability `copy-data`, локальная копия через agent или fallback обычной передачи. Нельзя делать hard link между двумя **изменяемыми** пользовательскими файлами без copy-on-write: запись в один иначе изменит другой. Смена всего backend на content-addressed storage не включена в P2.

`clone-content` проверяет версию источника, его доступность/права, expected назначения и квоту. Если источник изменён или недоступен, выполняется новый план; не используется ранее виденный путь без version check. Проверка результата и история назначения остаются такими же, как для обычной публикации.

**Пример.** Уже согласованный архив 12 GiB скопирован в соседний каталог. Если клиент достоверно установил одинаковое содержимое и backend поддерживает server-side copy, повторная передача 12 GiB с ПК не нужна. Но физическая копия на SFTP может занять время и дополнительное место. При обычном rename используется S11, а не копирование.

**Приёмка.** Скопированный идентичный файл с известным хешем не расходует клиентский content upload при capability. После изменения одной копии другая остаётся неизменной. Запрос dedup из другого scope ничего не раскрывает и не позволяет создать ссылку на чужие bytes.

## 6. Узкоспециализированные и точечные решения

Каждый пункт ниже — отдельная задача внедрения внутри системных механизмов. Они не подменяют S01–S14 и не должны выдаваться за достаточное исправление архитектуры.

### T01. Single-flight для родителей и ограниченный кеш разрешённых ID

**Где:** S06, клиент и WebDAV adapter. На один ключ `(root_id, epoch, parent_id, name_key)` существует только один выполняемый lookup/ensure. Остальные запросы ожидают его результат. Успешное соответствие сохраняется в индексе; in-memory кеш ограничен 8192 записями с вытеснением. Отрицательный ответ кешируется не более 2 секунд и не используется как разрешение безусловного overwrite.

Инвалидация приходит из журнала; `PARENT_NOT_FOUND`, namespace change и epoch mismatch инвалидируют ветвь. Завершившийся неуспешно Task не должен навсегда остаться в кеше.

**Пример:** 100 одновременно готовых файлов одного каталога вызывают одну подготовку родителя. **Тест:** 100 конкурентных обращений, затем удаление/восстановление родителя и повтор — без зависшего отрицательного кеша и дубликатов.

### T02. SQLite: один писатель, групповые транзакции и контролируемый WAL

**Где:** LocalIndex, operation store. Использовать WAL, `foreign_keys=ON`, `synchronous=FULL`, подготовленные выражения и одного писателя, принимающего ограниченные партии. Default batch — до 1000 строк либо 100 мс накопления, что раньше. WAL допускает чтение параллельно с writer, но не устраняет ограничение одного одновременного писателя [W22].

Курсор и порождённые задачи — одна транзакция. Не держать её во время HTTP/SFTP. Checkpoint выполнять фоново при WAL >64 MiB; длительно читающие операции не должны удерживать snapshot UI. Состояние лежит на локальном диске вне синхронизируемого дерева. `synchronous=OFF` для красивого benchmark запрещён.

**Пример:** 1000 событий приводят к пакетному upsert, не к 1000 независимым durable commits. **Тест:** отключение питания/kill между batch и cursor; после запуска нет пропущенных событий. WAL не растёт без ограничений при открытом окне прогресса.

### T03. SQL: убрать N+1, подтвердить индексы и сократить проекции

**Где:** Saturn repository. На G0 выполнить `EXPLAIN (ANALYZE, BUFFERS)` в изолированной тестовой базе для прямого поиска child и для batch resolve. Переиспользовать существующий индекс, зафиксированный Codex [L01, строка 47]. Добавлять индекс только при доказанном отсутствии нужного доступа или новой семантики ключа; не дублировать одинаковые B-tree.

Для выдачи sync-метаданных выбирать только ID, parent, name, type, size, hash, version и last_seq; не поднимать ACL-граф, thumbnails и полные ORM-объекты по каждому файлу. Batch lookup — set-based query с ограниченным входом. Строки root clock блокируются всегда в одном порядке; несколько roots одной транзакцией P1 не изменяются.

**Пример:** запрос 500 children не создаёт 500 перечислений каталога и 500 дополнительных загрузок parent. **Тест:** фактическое число SQL-запросов на batch ограничено фиксированным числом служебных запросов плюс действительно необходимые backend-действия.

### T04. Переиспользование HTTP-соединений, streaming и отдельные timeout

**Где:** WebDavSyncClient/новый SyncApiClient. Долгоживущий `HttpClient` либо управляемый пул через factory, ограниченный `MaxConnectionsPerServer`, переиспользование TLS-соединений; корректное обновление DNS через lifetime соединений [W21]. Не создавать новый transport на файл. HTTP/2 использовать при поддержке, но не считать его заменой сокращения запросов.

Разделить connect timeout 15 с, metadata request timeout 30 с и inactivity timeout content-потока 120 с. У большого файла нет общего лимита 15 минут, пока есть подтверждённый прогресс. Явно освобождать response/stream. Размер chunk body известен заранее; HTTP-прокси не должен буферизовать весь многочасовой файл.

**Пример:** файл 40 GiB на медленной линии не падает просто из-за большой общей длительности. **Тест:** потеря прогресса обрывает только операцию; медленный, но движущийся поток продолжает работать; количество TLS handshakes не равно числу файлов.

### T05. Настроить SFTP request window, а не только число файлов

**Где:** backend adapter. OpenSSH различает число outstanding SFTP requests и размер request buffer [W23]. На конкретной библиотеке проверить, не ждёт ли код завершения каждого WRITE перед отправкой следующего. Начальная цель: 16 запросов по 64 KiB на поток, если библиотека/сервер поддерживают такой размер; фактические пределы согласуются и учитываются в memory budget.

При RTT 100 мс один ожидаемый ответ на каждые 32 KiB даёт условный потолок около 0,31 MiB/s на таком последовательном участке. Окно в 1 MiB может поднять сетевой предел примерно до 10 MiB/s, пока нет другого bottleneck. Это расчёт `window/RTT`, не измерение нашего сервера.

Соединения переиспользуются; один session/channel не делится конкурентно, если библиотека это не гарантирует. **Тест:** нагрузка на один большой файл при фиксированных file workers, сравнение окна 1/4/16/32; не превышать суммарный лимит backend RAM и I/O.

### T06. Адресный debounce с максимальным ожиданием и поколениями

**Где:** dirty queue. Для одного объекта объединять события за 750 мс тишины, но выпускать кандидата не позднее 5 секунд с первого события. Постоянная запись в `build.log` не должна откладывать `notes.md`. Таймер вычисляется по monotonic clock; `first_dirty_at` не обнуляется каждым событием.

Операция получает поколение при планировании. Новые события повышают observed generation. После завершения удаляется только обработанная версия dirty-work, не вся строка «этот путь». USN и watcher могут сообщить одно изменение дважды; объединение допускает лишнюю локальную проверку, но не две одинаковые публикации.

**Пример:** 40 событий редактора за секунду превращаются в одну передачу конечной стабильной версии. **Тест:** непрерывные события одного файла, параллельная правка другого и completion старого поколения не приводят к starvation или потерянной правке.

### T07. Перечисление метаданных без массивов и лишних stat

**Где:** LocalScanner. Использовать потоковое перечисление, например адаптер на `FileSystemEnumerable<T>`, позволяющий фильтровать/проецировать entries [W27]. Не применять `GetFiles(...AllDirectories).ToArray()`, глобальные сортировки и несколько HashSet полного дерева. Сканировать каталогами, сохранять завершённость и идентичности. Повторно запрашивать metadata только если доступная entry не содержит нужного поля или нужно подтвердить стабильность перед передачей.

Фильтры вычисляются до рекурсивного входа в заведомо исключённую ветвь. При access error ошибка сохраняется для области; настройка «ignore inaccessible» не должна незаметно сделать сканирование полным. Для неизвестного диска начинать с одного enumerator.

**Пример:** 68 000 каталогов находятся в дисковой очереди, а не в тысячах рекурсивных Task. **Тест:** дерево глубиной 200 и широкий каталог на 100 000 файлов; память ограничена, stack overflow отсутствует, ошибочная ветвь не считается удалённой.

### T08. Версионированные исключения и прогноз эффекта до применения

**Где:** Root policy, scanner, planner. Правила исключения имеют `rules_version`, dry-run отчёт о числе объектов/байтов и явный режим изменения. Служебные файлы Neptune/Saturn всегда вне области; пользовательские `.git`, `node_modules`, `.venv`, `dist`, `.audit` не исключаются автоматически. Это часть пользовательских данных, пока пользователь не решил иначе.

Новая исключённая ветвь получает `UNMANAGED_PRESERVED`: клиент перестаёт управлять ею, но не удаляет уже существующую серверную копию. Возврат в managed-scope запускает adoption/snapshot сравнение, а не слепой overwrite. Удаление ранее сохранённого по новым правилам — отдельный подтверждённый план.

**Пример:** исключение `node_modules` уменьшает будущую работу, но серверная копия остаётся до отдельной очистки. **Тест:** включение/выключение одного правила во время bootstrap не меняет смысл уже подтверждённых операций без перепланирования.

### T09. Имена, case collisions, ссылки и особенности NTFS

**Где:** общий NameCodec и filesystem adapter. Исходное имя сохраняется без автоматического переименования; collision key имеет явно версионированную семантику. Для `portable_v1` нормативно выбрать NFC + locale-independent Unicode full case fold по таблицам Unicode 15.1.0 + повторный NFC той же версии. Использовать общие/default mappings, не Turkic-specific вариант. Это выбранная фиксированная версия протокола, а не утверждение о последней версии Unicode. Версия таблиц фиксируется в сборке и capabilities; C# и сервер используют одни тестовые векторы, а не меняющиеся правила системной locale. Это консервативное правило переносимости, которое может отклонять пары имён, допустимые на отдельной файловой системе. Новые roots используют `portable_v1`. Мигрируемый root сохраняет явно зарегистрированный `legacy` codec с фактической прежней семантикой до dry-run проверки всех имён; неподдерживаемый клиентом legacy codec блокирует переход, а не включает другое сравнение имён молча. Текущий repository не переводится на новую collation без проверки уже существующих коллизий. Переключение codec — отдельная versioned migration и новое поколение namespace, без автоматического переименования пользовательских файлов.

Запрещены абсолютные пути, `.`/`..`, разделители внутри имени, NUL, зарезервированные Windows-имена/символы и выход за root; ограничения Win32 проверяются по [W28]. Коллизия даёт `NAME_CONFLICT`, не выбор «первого файла». Длинные пути проверяются по реальным возможностям обоих концов; сокращать имя молча запрещено.

Symlink/junction/reparse-point по умолчанию не обходятся и получают видимое UNSUPPORTED_LINK. Hard links передаются как отдельные обычные записи содержимого с предупреждением о непереносимой link-семантике; файловая идентичность всё равно используется для обнаружения изменений. ADS/ACL не объявляются сохранёнными, пока нет специального адаптера.

**Тест:** `Readme`/`README`, составной Unicode, junction за пределы root, цикл и повторно использованный file ID не приводят к потере или отправке чужих данных.

### T10. Справедливая очередь по байтам и времени, без голодания больших файлов

**Где:** Scheduler S09. Для data lane использовать weighted deficit round-robin с квантами передаваемых байтов, а не выбором минимального файла. Default доли под нагрузкой: 25% для текущих изменений, 65% bootstrap, 10% recovery; незанятая доля немедленно заимствуется. Metadata dependencies обслуживаются отдельным небольшим бюджетом.

Большие файлы передаются частями; очередь может переключиться между частями, не разрушая upload session. Если задача ждёт более 30 секунд при доступном ресурсе, её возраст повышает приоритет. Доля не гарантирует физическое время при SOURCE_BUSY/ошибке прав — blocked tasks выводятся отдельно.

**Пример:** добавленный 10 KiB документ попадает на сервер во время загрузки 20 GiB видео, но видео продолжает продвигаться. **Тест:** бесконечный поток маленьких файлов не оставляет большой файл без подтверждённых chunks; одна активная папка не вытесняет остальные roots.

### T11. Нулевые файлы и metadata-only обновления без content upload

**Где:** Planner, operations API. Файл длины 0 имеет известный SHA-256 пустой последовательности; его можно создать операцией `create-empty` без upload-session. Пустой каталог — отдельный ensure, не псевдофайл. Изменение только поддерживаемого mtime/атрибута без изменения содержимого становится `patch-metadata` с expected version.

Событие `metadata changed` не доказывает отсутствие content changes: перед выбором операции проверить доступное поколение/журнал и сохранённый hash. Не следует создавать новую пользовательскую content-version только из-за времени последнего доступа. Метаданные, которыми sync не управляет, не должны запускать передачу.

**Пример:** изменение mtime у 500 достоверно неизменных файлов передаёт пакет описаний, не перечитывает и не загружает их содержимое. **Тест:** файл, в котором одновременно изменены bytes и mtime, не проходит ошибочно metadata-only; 100 000 пустых файлов обрабатываются без 100 000 сессий передачи.

### T12. Избирательное сжатие метаданных и транспортных данных

**Где:** HTTP API/batcher. Метаданные больше 16 KiB передавать с согласованным gzip; жёсткий предел проверяется и для распакованного объёма. Не сжимать повторно JPEG, ZIP, видео и другие обычно несжимаемые данные вслепую. Content compression по умолчанию выключена; в P3 допускается отдельная capability.

Для пробного content-сжатия использовать уже прочитанный префикс, не дополнительный проход исходного файла. Включение — ожидаемое сокращение не менее 15% при свободном CPU budget и подтверждённом сокращении end-to-end времени. Хеши считаются по исходным bytes, размер source сохраняется отдельно от wire size. Механизм не приписывается Sync.com.

**Пример:** JSON-индекс из тысяч строк экономит WAN-трафик; передача `.7z` не тратит CPU на бессмысленное сжатие. **Тест:** highly compressible и malicious compressed payload ограничиваются по распакованному размеру; chunk hash не зависит от выбранной wire compression.

### T13. Классифицированные повторы, Retry-After и circuit breaker

**Где:** HTTP/backend adapters, operation scheduler. Сетевой reset, timeout, 408, 429 и временные 5xx переводят **конкретную операцию** в RETRY_WAIT. Использовать `delay=random(0,min(60s,1s*2^attempt))`, уважать Retry-After как нижнюю границу. При потере ответа сначала query operation status. После 8 безуспешных попыток — WAIT_CONNECTIVITY/DEGRADED с редкой проверкой, не сброс root.

401 допускает одно обновление credential через существующий механизм; повторный отказ блокирует. 403 — права; 409/412 — перепланирование/конфликт; 413 — уменьшение неподтверждённой партии; 410 — восстановление курсора; quota exhaustion — ожидание освобождения места. 5 похожих backend failures за 30 секунд открывают breaker на 60 секунд; затем одна проба.

**Пример:** краткая перегрузка Saturn не запускает повторный общий scan на обоих ПК. **Тест:** шторм 429 ограничивает число запросов; новые ошибки прав не бесконечно повторяются как сетевые.

### T14. Admission control по байтам, свободному месту и жизненному циклу temp

**Где:** ingress, backend executor, локальный spool. До приёма зарезервировать объём текущей партии/части и требуемое место конечной новой версии с учётом сохранения старой. Бюджеты относятся отдельно к диску Neptune, ingress Saturn и конечному backend. Один большой файл не обязан полностью помещаться в ingress: части последовательно выводятся в backend temp, освобождая rolling budget.

100 GB обсуждаемого промежуточного буфера — не лимит общего root и не ускорение медленного backend само по себе. При заполнении буфера upload тормозится. Клиент не удаляет исходные данные на основании RECEIVED.

GC освобождает только temp, для которого нет активной lease, ссылки операции и обязательства восстановления. Удаление по одному возрасту файла запрещено. По умолчанию истёкшие temp сначала попадают в отчёт на очистку; активный upload продлевает lease.

**Пример:** root 166 GB синхронизируется через ingress 8 GiB порциями. **Тест:** disk full останавливает новые операции, не портит SQLite и не удаляет bytes уже опубликованных файлов.

### T15. Статусы по mapping и фазам, а не общие счётчики Storage

**Где:** CLI/UI. Отдельно показывать discovered, indexed, planned, directories ready, content received, backend verified, published, conflicted, blocked и progress unknown. Счётчики привязаны к root и run/checkpoint, а не всему Storage. Значение «1811 файлов на сервере» не является прогрессом конкретной `C:\.projects`.

`IN_SYNC` разрешён только при достоверной области, обработанном целевом cut, пустых необходимых очередях и отсутствии конфликтов/blocked данных. Временная тишина watcher означает «нет известных изменений», не безусловную проверку физических bytes. Ошибка UI и popup имеют один error ID; повторное отображение не увеличивает количество инцидентов.

**Пример:** «Принято 40 GiB; проверено на диске 12 GiB; осталось 8000 операций; scan ещё идёт». **Тест:** сервер принял все bytes, но readback завершился ошибкой — интерфейс не показывает зелёное завершение.

### T16. Идентичность корня, защита от подмены тома и единственный владелец

**Где:** RootRegistry. Сохранять volume identity, файловую идентичность корня, canonical location, mapping ID и device identity. В начале работы проверять именно их: та же буква `D:` может указывать на другой носитель. При несовпадении — ROOT_IDENTITY_CHANGED, запрет автоматических удалений и предложение отдельного adoption-процесса.

Не создавать marker в пользовательском root без необходимости: служебная идентичность хранится снаружи. Для файловых систем без устойчивого ID привязка помечается weaker, требует явного подтверждения после сомнительного переподключения. На mapping действует межпроцессный mutex и server writer ownership. В P1 пересекающиеся local roots или перекрывающиеся destination roots одного writer запрещены, пока не реализована отдельная политика перекрытия.

**Пример:** отключён внешний диск, путь остался пустой точкой монтирования — содержимое сервера не удаляется. **Тест:** запуск двух exe, замена буквы тома, symlink-подмена корня и миграция профиля не создают два писателя.

### T17. Профили захвата активных данных и ограниченные snapshots

**Где:** Source adapter, необязательный Windows snapshot module. Обычные файлы используют guard S08. Для данных приложения, которым нужна групповая согласованность, выбран профиль `application_export`; для поддерживаемых томов — `vss_snapshot` с известным составом writers и уровнем consistency. VSS координирует requester, writer и provider; просто открыть копию одного файла недостаточно для согласованности базы [W29].

Snapshots имеют бюджет диска и срок жизни; права службы ограничены. При недоступности writer/application export возвращается `SOURCE_SNAPSHOT_REQUIRED`. Не копировать активную SQLite базу с отсутствующим WAL как будто это согласованный источник. Резервная копия собственного состояния Neptune выполняется SQLite Backup API [W30].

По умолчанию ни остановка пользовательских приложений, ни VSS всего тома без настройки не выполняются. Долго SOURCE_BUSY файлы показываются отдельно; они не блокируют остальные.

**Пример:** backup базы выполняется через согласованный export, затем export синхронизируется обычным потоком. **Тест:** снимок исчезает после crash/TTL, источник меняется — checkpoint не переиспользуется для другой версии.

### T18. Метрики усиления операций и низконакладный журнал

**Где:** все стадии. Измерять `HTTP requests / published file`, `SQL queries / metadata batch`, `SFTP ops / file`, `source_read_bytes / unique_source_bytes`, pool wait и latency стадий. Не писать path/file ID как label time-series: это создаёт сотни тысяч рядов и самостоятельную проблему ресурсов.

Подробные пути сохраняются в ограниченном структурированном audit log с operation/error ID и без секретов. Счётчики агрегируются раз в секунду; per-byte запись в базу запрещена. Проверка hash mismatch остаётся несэмплируемой, обычные успешные подробности можно семплировать. Экспорт диагностического пакета маскирует credentials и персональные пути по выбранной политике.

**Пример:** после исправления MKCOL видно падение request amplification, но `backend_verify_seconds` становится главным временем — следующий шаг направлен в S10, а не на случайное увеличение потоков. **Тест:** включение production-метрик не снижает throughput более чем на 5% на эталонном стенде.

### T19. Long-poll уведомления как сигнал к чтению надёжного журнала

**Где:** Sync API и scheduler. По умолчанию одна ожидающая `changes?wait=25s` на root, с event-driven пробуждением по новой опубликованной ревизии. Не выполнять SQL-поллинг каждую секунду для каждого клиента. Подписка/уведомление лишь ускоряет чтение feed; оно не заменяет журнал и курсор. Уведомление, потерянное при рестарте, восстанавливается обычным запросом после сохранённого курсора.

Таймер раз в 5 минут остаётся health check/watchdog, не инициатором общего scan. На множестве roots можно использовать общий device notify stream с последующим чтением конкретных feeds; в P1 достаточно root long-poll. При отсутствие WebSocket/SSE не менять гарантии.

**Пример:** сервер изменил один документ — клиент узнаёт быстро, но не делает HEAD остальных. **Тест:** потерять 100% уведомлений, сохранив возможность чтения feed; следующая проверка корректно восстанавливает состояние без полного дерева.

### T20. Дешёвый UI и shell-status без повторного обхода

**Где:** Windows UI, shell integration, status service. Значки и прогресс читаются из materialized status/index. Один redraw не должен запускать sync, hashing или запрос Saturn. Кешировать ответ visible-path status на 2 секунды и инвалидировать адресно при смене состояния; выдавать его пачкой. Список ошибок/операций в UI виртуализирован и постраничен.

Обновления прогресса интерфейса объединять до 4 раз в секунду, summary — раз в секунду. Не создавать ObservableCollection всех 395 000 файлов и отдельный timer на каждый. Шаблон «меньше фоновой работы и затрат на отображение статуса» согласуется с направлением обновления Sync [W01], но конкретный кеш и интервалы — наш проект.

**Пример:** открытие папки на 30 000 entries не вызывает столько же запросов к backend. **Тест:** UI открыт/закрыт при том же наборе; throughput отличается не более чем на 5%, а рабочая память не растёт пропорционально размеру всего дерева.

## 7. Нормативные модели данных и контракты

### 7.1. Общие правила форматов

API имеет префикс `/api/sync/v1`. Идентификаторы — непрозрачные строки длиной до 128 ASCII-символов, формируемые соответствующей стороной; production IDs используют UUID, примеры ниже используют короткие условные значения. Клиент не выводит путь или полномочия из ID. SHA-256 — 64 lowercase hex-символа; размер — неотрицательный integer64. В JSON **все integer64 передаются десятичными строками**, включая seq, generation, offsets и sizes; это исключает потерю точности в TypeScript/JavaScript. Малые лимиты и количества элементов могут быть JSON numbers.

Невалидный UTF-8, дублированные JSON keys, отрицательные размеры, неизвестный enum, float вместо integer64 и несоответствие Content-Length отклоняются до публикации. `null` допустим только для явно nullable полей. Для fingerprints использовать SHA-256 от canonical JSON по JCS [W31]; integers64 остаются строками, timezone/date форматы фиксированы. Unknown response fields клиент может игнорировать для совместимости; unknown request fields, меняющие семантику записи, сервер отклоняет.

`expected` имеет строго один из двух видов:

```json
{"kind":"absent"}
```

```json
{"kind":"version","node_id":"n-report","version":"v8"}
```

`absent` проверяется по root/parent/name в момент публикации; `version` — по существующему node. Подстановка свежей версии вместо baseline при 412 запрещена. В legacy single-object WebDAV эти условия адаптируются к корректным HTTP preconditions; слабый ETag не принимается как CAS/content hash [W26].

### 7.6. Snapshot + feed: контракт и пример

Запрос создания:

```json
{"client_request_id":"snapshot-request-12","purpose":"bootstrap"}
```

Начальный ответ `202`:

```json
{"snapshot_id":"snap-12","state":"BUILDING"}
```

READY-метаданные:

```json
{
  "snapshot_id":"snap-12",
  "state":"READY",
  "server_epoch":"epoch-7",
  "cut_seq":"12000",
  "entries_cursor":"opaque-page-start",
  "changes_cursor":"opaque-feed-after-12000",
  "lease_seconds":7200,
  "absolute_lifetime_seconds":86400
}
```

Lease продлевается каждые 15 минут до максимальной жизни 24 часа. Snapshot содержит только metadata, поэтому клиент должен закончить его импорт до истечения суток даже при многодневной передаче bytes. При истечении срока — новый snapshot, а не перезагрузка уже опубликованных файлов. `changes_cursor` подписан сервером и привязан к root/epoch/scope; его содержимое клиент не редактирует.

Пример feed:

```json
{
  "server_epoch":"epoch-7",
  "from_exclusive":"12000",
  "to_inclusive":"12002",
  "items":[
    {
      "seq":"12001",
      "kind":"upsert",
      "node_id":"n-a",
      "parent_id":"n-src",
      "name":"a.cs",
      "type":"file",
      "size_bytes":"8192",
      "content_sha256":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
      "version":"v17",
      "operation_id":"op-a-42"

      "seq":"12002",
```

Хеш из повторяющихся `a` здесь — демонстрационное значение формата, не хеш реального файла. В реальных запросах тесты используют вычисленные hashes.

### 7.8. Формат пакета файлов и результаты

`Content-Type: multipart/related; boundary=<random>`; первая часть — UTF-8 JSON-manifest не более 4 MiB, затем parts с уникальным `Content-ID: <operation_id>` и `Content-Length` по manifest. Имена файлов не используются как имена temp на сервере. P2 не использует ZIP/TAR parser и потому не требует извлекать пользовательские пути из архива. Общий budget полезных bytes — 32 MiB плюс ограниченные metadata/headers.

```json
{
  "batch_id":"batch-700",
  "server_epoch":"epoch-7",
  "rules_version":"rules-3",
  "items":[
    {
      "operation_id":"op-a-42",
      "source_generation":"42",
      "source_identity":"source-a-capture-42",
      "parent_id":"n-src",
      "name":"a.cs",
      "size_bytes":"8192",
      "sha256":"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa",
      "expected":{"kind":"version","node_id":"n-a","version":"v16"}
    },
    {
      "operation_id":"op-b-1",
      "source_generation":"1",
      "source_identity":"source-b-capture-1",
      "parent_id":"n-src",
      "name":"b.cs",
      "size_bytes":"2048",
      "sha256":"bbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbbb",
      "expected":{"kind":"absent"}
    }
  ]
}
```

Сервер регистрирует manifest и резервирует объём, затем принимает части. Полный совпадающий ранее принятый элемент не пишется второй раз. Если клиент всё же послал его body повторно, сервер может безопасно вычитать и отбросить его в пределах лимитов; ускоренный клиент предварительно делает status query и не посылает лишнее.

Пример `202`:

```json
{
  "batch_id":"batch-700",
  "items":[
    {"operation_id":"op-a-42","state":"PUBLISHED","node_id":"n-a","version":"v17","seq":"12001","durability":"verified_readback"},
    {"operation_id":"op-b-1","state":"BACKEND_WRITING"}
  ]
}
```

HTTP `202` означает принятый асинхронный запрос, а не финальный успех всех элементов. `200` для status query также не означает публикацию: проверяется per-item state. HTTP-level malformed request — 400/413; содержательные ошибки отдельных валидных операций — per-item error. Код 207 WebDAV для этого собственного JSON API не требуется.

### 7.9. Большие файлы и resume

`uploads:create` принимает immutable intent без общего SHA-256, если файл ещё не дочитан, но с фиксированными source identity/generation, size, назначением и expected. Сервер выдаёт upload ID и chunk size 8 MiB. Chunk index нулевой; `offset=index*chunk_size`; все части кроме последней ровно chunk_size. Zero-length передаётся через T11.

Часть читается в ограниченный buffer, SHA-256 вычисляется до её PUT. Заголовки: `Content-Length`, `X-Chunk-SHA256`, `X-Operation-ID`, `X-Server-Epoch`. Повтор того же index с тем же hash/length возвращает текущее состояние; другой hash — `409 CHUNK_MISMATCH`, не перезапись.

В P1/P2 один большой файл передаёт части последовательно; несколько файлов идут параллельно. Внутренняя параллельность одного файла не нужна для первого результата и выключена. Backend adapter может независимо иметь pipelining SFTP writes T05.

Seal содержит итоговый размер, общий SHA-256 и хеш списка `{index,size,chunk_hash}`. Общий SHA-256 считается по полному содержимому, **не** как hash от склейки chunk hashes. Seal неизменяем: второй другой digest запрещён. Публикация запускается только после наличия всех частей и успешной stored verification S10.

После перезапуска сначала запросить server operation/upload status. Если source version достоверно та же и части проверены, передать недостающее. При утрате достоверности источника повторно проверить сохранённые prefix chunk hashes/целое содержимое либо открыть сохранённый snapshot; при несовпадении старая операция отменяется, создаётся новое поколение. Сохранённое внутреннее состояние конкретной реализации SHA-256 не является межверсионным checkpoint-форматом. При необходимости общий хеш после resume вычисляется заново чтением source: это дополнительный I/O, но не повторная передача подтверждённых частей.

Статус `CHUNK_RECEIVED` означает наличие части в заявленном промежуточном состоянии, а не финальную сохранность файла. Если после crash часть больше не доступна/не проверяется, сервер честно возвращает её как missing. Исходник на ПК не удаляется; клиент может восстановить часть. Финальная квитанция выдаётся только по S10.

### 7.10. Namespace-операции и удаление дерева

Одна `operations:batch` содержит максимум 500 операций и 4 MiB metadata. Для каждого элемента обязательны ID, type, expected, root/epoch и выбранные поля:

| Type | Дополнительные поля | Условие |
|---|---|---|
| `move` | node_id, target_parent_id, target_name | Нет циклов; same root; доступ к обоим родителям; target absent или явно разрешённый replacement |
| `patch-metadata` | node_id, поддерживаемый набор атрибутов | Нет неподтверждённого content change |
| `create-empty` | parent_id, name | expected=absent; известный empty hash |
| `adopt-equal` | node_id, expected R, source generation, content hash | Серверная проверенная версия совпадает с local hash; не меняет bytes |
| `quarantine-delete` | node_id, baseline expected, plan_id/approval при массовом действии | Только ранее managed объект; откат через историю |
| `clone-content` | source node/version либо авторизованный content reference, destination | Capability и права источника; expected назначения |

В P1 удаление дерева — **логический план, раскрываемый в per-node postorder операции**. Сначала файлы и вложенные пустые каталоги, затем родитель. Каждая операция имеет собственный CAS; удаление каталога допускается только если в нём нет новых непредусмотренных детей. Это гарантирует защиту от неожиданного серверного файла без требования физически атомарно удалить 20 000 entries одной операцией. Fast subtree-delete по единой subtree revision не включён до отдельной capability; наличие одной логической команды не скрывает стоимость полного плана.

### 7.11. Ошибки и обязательные реакции

| Код | Реакция |

| `PARENT_NOT_FOUND` | Адресная инвалидация и resolve родителя |
| `TYPE_CONFLICT` / `NAME_CONFLICT` | Блок конкретного объекта; сохранить оба описания |
| `DEPENDENCY_FAILED` | Ждать исправления зависимости; независимые ветки продолжаются |
| `SOURCE_BUSY` / `SOURCE_CHANGED` | Отложить либо создать новое поколение; старый completion не завершает новое |
| `SOURCE_SNAPSHOT_REQUIRED` | Использовать настроенный snapshot/export профиль; иначе blocked |
| `ROOT_IDENTITY_CHANGED` | Остановить mapping и любые удаления; отдельная проверка привязки |
| `JOURNAL_GAP` | Восстановительный локальный обход/проверка по S03 |
| `OPERATION_ID_REUSED` / `CHUNK_MISMATCH` | Ошибка целостности протокола; не «лечить» overwrite |
| `HASH_MISMATCH` | Не публиковать; изолировать temp; ограниченный повтор и диагностика слоя |
| `RATE_LIMITED` / `TEMPORARY_BACKEND_FAILURE` | Backoff, общий limiter/breaker |
| `QUOTA_EXCEEDED` / `DISK_PRESSURE` | Прекратить новый ingress; не удалять историю/активные temp молча |
| `AUTH_REQUIRED` / `PERMISSION_DENIED` | Обновить разрешённый credential один раз либо blocked; не повторять дерево |
| `PUBLISH_IN_PROGRESS` / `BACKEND_UNCERTAIN` | Query status/recovery, не дублирующая запись |
| `UNSUPPORTED_CAPABILITY` | Выбрать описанный fallback, не понижать гарантию скрыто |
| `CANCEL_TOO_LATE` | Публикация уже произошла; отмена не превращается в скрытое удаление |

Каждая ошибка содержит `error_id`, `operation_id` при наличии, `root_id`, `stage`, `retryable`, безопасное описание, timestamp и diagnostic correlation ID. Stack trace хранится в диагностике, а не заменяет понятную причину в UI.

<a id="scenarios"></a>
## 8. Алгоритмы и сквозные сценарии

### 8.1. Начало работы root

Ниже псевдокод нормативного порядка, не готовый код существующей реализации.

```text
StartRoot(mapping):
    acquire interprocess ownership
    validate root/device/volume identity and configuration version
    negotiate server epoch, root policy and capabilities
    recover uncertain local and server operations by persisted IDs

    if local journal continuity is valid:
        capture new events into durable dirty queue
    else:
        mark local observation uncertain
        schedule resumable reconciliation; block inference-based deletes

    if remote index absent or epoch/cursor invalid:
        begin/import a new remote snapshot generation
    else:
        ingest changes after saved cursor

    run scanner, planner and bounded workers as independent modules
    do not start a second whole-tree pass because a worker is active
```

### 8.2. Построение операции

```text
Plan(entry):
    read L, B, R and observation validity
    if state unknown:
        enqueue targeted metadata/content verification; return
    if L and R match the agreed baseline:
        return NOOP
    if destination unobserved during bootstrap:
        use batch resolve; never infer ABSENT from missing snapshot page
    if L changed and R equals B:
        build an immutable intent against B
    else if content is verifiably equal:
        plan conditional ADOPT_EQUAL
    else:
        persist conflict; do not silently refresh baseline

    transaction:
        persist operation_id + source generation + expected + dependencies
        retain any newer observed generation as pending
```

### 8.3. Выполнение и подтверждение

```text
Execute(operation):
    if server already knows operation_id:
        apply known result or continue its incomplete stage
    wait for dependencies without occupying a transfer slot
    acquire global resource budget
    capture/read the intended source version
    transmit bytes or execute metadata operation
    retain source-generation association throughout the operation
    on unknown network outcome: query status before replay

ApplyPublishedReceipt(receipt):
    transaction:
        validate root/epoch/operation/fingerprint and returned digest
        update baseline to the actually acknowledged source generation
        record returned remote version
        keep the newest remote last_seq; never overwrite newer R by older reply
        complete only this operation's generation
        retain or create work for a newer local generation
```

Даже после собственной публикации R может уже содержать более новую чужую версию из feed. Тогда B становится версией нашей подтверждённой операции, а R остаётся более новым: Planner должен обнаружить remote divergence, а не затереть её запоздалым HTTP-ответом.

### 8.4. Первая загрузка в пустой корень

Профиль зарегистрирован, server snapshot на C показывает пустой root. Scanner обнаруживает `a/`, `a/src/`, 100 файлов и `b/`, но остальные тысячи каталогов ещё неизвестны. Directory ensure создаёт нужные parents; batcher готовит первую партию; большие файлы идут отдельными sessions. Продолжаются сканирование и сохранение новых operations.

Финальная граница bootstrap — полное обследование выбранной области, обработка событий до зафиксированного локального cut и наличие результата каждой необходимой операции соответствующего поколения. После этого root переходит в steady state; последующие изменения не заставляют повторять bootstrap. Непрерывно изменяющийся root может оставаться ACTIVE без ложного «завис на финальной проверке»; UI показывает возраст и число незавершённых текущих поколений.

### 8.5. Продолжение уже начатой загрузки текущего ПК

Сохраняются профиль, mapping, device identity и локальная база. Серверные уже созданные каталоги импортируются в индекс как существующие. Файлы, если успели появиться, сравниваются по доступным версиям и хешам; совпадение неизвестных mtime само по себе adoption не разрешает. Старые checkpoints принимаются только через migration adapter с проверкой формата, source identity и действительности upload session.

Например, до остановки создано 57 000 каталогов из 68 000. Новая версия не повторяет 560 000 MKCOL. Она получает серверные descriptors страницами, создаёт операции только для отсутствующих каталогов, а передачи начинает по мере готовности родителей. Если актуальных checkpoint нет, не обещается продолжение произвольного непроверенного temp по его размеру; готовые каталог/файл всё равно можно принять без повторного создания/передачи.

Число 57 000 здесь — сценарий из порядка величин исходного обсуждения, **не актуальный замер текущего процесса**.

### 8.6. Пустой повторный цикл на втором ПК

Индексы действительны, локальный журнал не дал относящихся к root изменений, сервер вернул пустое продолжение. План операций пуст. Результат: **0 HEAD на файл, 0 MKCOL, 0 content reads, 0 PUT и 0 PROPFIND дерева**. Допустимы один feed request, root health/lease exchange и чтение локального журнала; их число не зависит от 1700 или 395 000 файлов.

Если отсутствует надёжное локальное наблюдение и клиент только что был выключен, честно выполняется fallback S03. Это другой сценарий; его нельзя смешивать с benchmark пустого непрерывного цикла.

### 8.7. Новый файл во время большой первой загрузки

Пользователь создал `urgent.md`. Событие попало в dirty queue, прошло адресный debounce, родитель уже известен. Файл получает current-change priority и отправляется в течение доступной доли ресурса, не ждёт конца очереди bootstrap. Если его родитель ещё не создан, dependency повышается в приоритете вместе с потомком.

При изменении файла во время spool preparation новая версия остаётся dirty. Если передача старой версии завершилась, B фиксирует её честно. Это не повод очистить последнее событие по совпадающему имени.

### 8.8. Восстановление при истекшем курсоре и недоступной ветви

Server отвечает 410. Клиент оставляет B и operations, импортирует snapshot нового поколения и продолжает сравнение. Одновременно локальный `project-c` оказался недоступен. Для него L=UNKNOWN и scan incomplete; серверные файлы этой ветви не планируются на удаление. В остальных ветвях обновления идут.

Когда доступ восстановлен, выполняется адресная сверка `project-c`. Полный root scan не повторяется только потому, что одна ветвь долго была blocked. Если потеря журнала затронула весь том и неизвестна область пропуска, допустима полная метаданная сверка — скрывать эту неопределённость нельзя.

### 8.9. Публикация состоялась, ответ потерян

Saturn переместил проверенный temp, зафиксировал metadata+change+receipt, но HTTP-соединение оборвалось. Neptune сохраняет `OUTCOME_UNKNOWN` как локальную разновидность RETRY_WAIT и вызывает batch status. Получив PUBLISHED с правильными operation ID/epoch/digest, он обновляет B. Второго файла, второй пользовательской версии и повторной передачи не возникает.

Если crash был после physical rename, но до SQL commit, backend intent остаётся uncertain. Recovery изолированно сравнивает фактические temp/final/history с ожидаемыми хешами и завершает или откатывает публикацию. Клиент ждёт это восстановление, а не запускает конкурирующий PUT в тот же путь.

### 8.10. Отмена и изменение намерения

Пользовательская пауза останавливает выдачу новой работы, но позволяет завершить текущую небольшую безопасную часть и сохранить checkpoint. Cancel непубликованной операции освобождает её собственные зависимости/резервы только после подтверждения сервера. Cancel опубликованной операции возвращает `CANCEL_TOO_LATE`; восстановление предыдущей версии — новая журналируемая операция, а не стирание истории.

Если source generation изменилось до передачи, можно supersede ещё не отправленное намерение. Если сервер уже принял bytes, сначала выясняется его состояние; новая операция не переиспользует старый operation ID. Для двух разных версий одного объекта публикации упорядочиваются зависимостью, чтобы старое поколение не оказалось последней версией после нового.

### 9.2. Правила применения

Feature flags выше стартуют выключенными для staged rollout; исправления P0 и постоянная модель не откладываются до их включения. После gate соответствующий флаг включается для canary root и затем для остальных. Capabilities отражают **эффективное** значение, а не наличие кода в дистрибутиве.

`bandwidth_limit=null` означает отсутствие дополнительного лимита клиента, не разрешение игнорировать server admission. Если в профиле уже задано, например, 8 MiB/s, миграция сохраняет его; не увеличивает сеть автоматически. Ни один budget не умножается на число mappings.

Managed buffers не равны всей памяти процесса: есть SQLite page cache, TLS/socket buffers, runtime и UI. Их наблюдают отдельно; SLA рабочей памяти задаётся в разделе 11. Перед выделением buffer исполнитель получает memory token. Server ingress reserve может быть меньше размера файла, но backend reserve учитывает всю незавершённую новую версию и политику истории.

Параметр `backend_writer_processes: 1` запрещает активную запись второго процесса, но не означает строго одну операцию I/O: внутри writer допускаются независимые workers и pipelining. Истёкшая worker lease не даёт второму процессу право конкурировать с не остановленным первым SFTP writer.

При недоступности свободного места, несовместимых лимитах или неизвестной capability выводится конкретная причина. Пустой root не становится «ошибкой синхронизации» из-за отсутствия опционального ускорения. Но строгая гарантия, которую backend не поддерживает, не подменяется более слабой без явной смены конфигурации.

## 10. Наблюдаемость, расчёт эффекта и границы ускорения

### 10.1. Что измерять до и после

Для каждого прогона сохранять manifest версии: client build hash, server image digest, schema/API versions, OS/filesystem, CPU/RAM, backend capability, storage pool, bandwidth limits, RTT и профиль набора данных. Это позволяет отличить эффект кода от другого сервера или меньшего объёма.

| Группа | Обязательные метрики |
|---|---|
| Обнаружение | files/dirs discovered per second; scan duration; scan incomplete count; source stat/read calls; USN records received/filtered; watcher gaps |
| План | NOOP/adoption/create/update/move/delete/conflict counts; oldest dirty age; dependency wait; unproven states |
| Транспорт | HTTP requests по method/route; TLS handshakes; client ingress bytes; retry bytes; active sessions; batch fill ratio |
| Backend | SFTP lookup/list/open/write/read/rename/flush counts; second-hop bytes in/out; pool wait; physical create/verify/publish latency |
| Состояние | SQLite commit latency/WAL size; PostgreSQL queries/lock wait; snapshot age; cursor lag; outstanding intents |
| Результат | published files/s, backend verified bytes/s, end-to-end edit-to-publish latency, resume recovery time |
| Ресурсы | process working set; managed buffers; CPU; I/O queue/latency; disk free/reserved; ingress backlog |
| Целостность | hash mismatches; uncertain operations; invalid preconditions; missing history/receipts; scrub lag |

Рекомендуемые производные коэффициенты:

```text
metadata_amplification = metadata_http_requests / max(1, changed_or_new_objects)
source_read_amplification = source_bytes_read / max(1, bytes_of_source_versions_processed)
retry_amplification = retransmitted_bytes / max(1, unique_bytes_needed)
publication_efficiency = published_files / max(1, backend_file_operations)
```

Для пустого цикла отношения с нулём не интерпретируются: проверяются абсолютные нули по запрещённым операциям. Для resume и delta считать дополнительное чтение отдельно, чтобы не смешивать его с one-pass whole-file путём.

### 10.2. Модель времени

Нижняя оценка для конвейера:

```text
T >= max(
    unique_bytes / useful_client_upload_rate,
    backend_written_bytes / useful_backend_write_rate,
    backend_verify_bytes / useful_backend_read_rate,
    physical_file_operations / sustainable_backend_ops_rate,
    required_source_reads / useful_local_read_rate
)
```

Оценка не включает всё ожидание зависимостей, повторов и конфликтов. Этапы могут перекрываться, поэтому механически складывать все приведённые нижние оценки нельзя. Но при конкуренции чтения и записи за один HDD независимость тоже нельзя предполагать.

Для примера 166 000 000 000 байтов при полезных 8 MiB/s требуют около **5,50 часа только клиентской передачи**. Для 395 000 файлов:

| Устойчивая скорость окончательной публикации | Время на число файлов |
|---:|---:|
| 10 файлов/с | 10,97 часа |
| 50 файлов/с | 2,19 часа |
| 200 файлов/с | 32,9 минуты |

Все эти значения — расчёты, не результаты теста production. Показатель приёма в ingress 200 файлов/с при публикации 10 файлов/с означает растущий backlog, а не готовое 20-кратное ускорение.

### 10.3. Где ожидается кратный эффект

| Изменение | Ожидаемый структурный эффект | Что не обещается |
|---|---|---|
| Уникальная подготовка каталогов | Для оценённого дерева порядка 56-кратного сокращения соответствующих логических повторов | 56-кратное сокращение всей длительности |
| Snapshot/batch metadata | Сотни страниц вместо сотен тысяч per-object round trips, если scope известен целиком | Столько же малое число физических mkdir/open |
| Delta-index steady state | Нулевые per-file запросы для неизменённых объектов; работа по изменениям | O(1) чтение всего USN при бурной активности тома |
| Пакеты малых файлов | Сокращение числа HTTP upload процедур примерно по среднему наполнению пакета | Исчезновение файловых операций backend |
| Конвейерное хеширование | Устранение лишних предварительных чтений источника в обычном whole-file пути | Отказ от backend readback или бесплатная delta-подготовка |
| Ограниченная параллельность | Перекрытие независимых ожиданий и загрузка доступных ресурсов | Линейное ускорение с любым числом workers |
| Storage-local verification | Удаление WAN-чтения для проверки при сохранении локальной проверки диска | Более быстрый физический диск |
| File/block reuse | Сокращение повторной передачи уже имеющегося содержимого | Мгновенная копия на native-tree backend без соответствующей возможности |

Числа 3×/5×/10× не назначаются всем решениям искусственно. Показать кратное уменьшение лишних операций можно ещё до физического benchmark; подтвердить кратное ускорение всей задачи можно только одинаковыми прогонами на конечном backend.

### 10.4. Решения, которые не принимать за основное исправление

Один ZIP на весь root меняет гранулярность обновления и восстановления. Увеличение buffer до 100 GB лишь временно поглощает отставание. Снижение частоты полного обхода оставляет стоимость и задержку обнаружения. Сотни одновременных файлов создают contention и повторные ошибки. Отключение хешей, durability или антивирусной защиты скрывает проблему ценой гарантии; по умолчанию запрещено. Увеличение лимита PROPFIND с 100 000 до миллиона без изменения памяти/пагинации переносит дефект.

Миграция на physical pack storage, обязательная дедупликация всех данных, Kafka и файловые placeholders не входят в минимальное решение. Они допустимы как отдельные проекты только при доказанной пользе и согласованной новой модели доступа.

## 11. Испытания и критерии приёмки

### 11.1. Входная проверка перед performance-прогоном

Подтвердить root/device identity, точные build hashes, миграцию схемы, capabilities, свободное место на трёх слоях, независимость тестового root, отсутствие другого writer и одинаковые лимиты канала. Зафиксировать включённую backend verification: сравнивать старый проверяемый путь с новым непроверяемым запрещено. Набор данных должен иметь воспроизводимый manifest хешей; конфиденциальное содержимое `.projects` не требуется для синтетического benchmark.

Для сетевых профилей использовать измеренный baseline и отдельно искусственные RTT 20/80/150 мс, ограничение bandwidth и редкие разрывы. Тесты на HDD и SSD разделяются. Условия cold/warm cache указываются в отчёте; пять прогонов не смешиваются с одним «лучшим» результатом. Сквозной набор запускать минимум трижды и публиковать медиану и p95 стадий, а не только рекорд.

### 11.4. Измеримые performance-требования

**Жёсткие структурные условия:** A02 — абсолютный ноль per-file сетевой работы; initial directory work не пропорциональна `files × depth`; RAM не содержит полный metadata tree; в normal sync нет полного remote enumeration; завершённые операции не повторяют bytes после обычного restart; очереди ограничены.

**Эталонный стенд:** фиксируется на G0, минимум 4 логических CPU, 8 GiB RAM, локальный SSD и изолированный backend-профиль с объявленным RTT/каналом. Это тестовое условие, не требование заменить пользовательский ПК.

Для этого стенда принять начальные цели:

| Метрика | Цель |
|---|---|
| Пустой цикл без long-poll wait, 1700 против 500k entries | p95 до 2 секунд после получения сигнала; число requests отличается не более чем на постоянное число служебных операций |
| Первое получение readied file при bootstrap | Передача начинается до конца scan; p95 до 5 секунд после готовности источника и родителей при доступном ресурсе |
| Изменение обычного малого файла в steady state | p95 edit-to-publish до 5 секунд на здоровом стенде, без SOURCE_BUSY |
| Рабочая память sync engine на 500k objects | Цель до 384 MiB без UI; managed buffer caps всегда соблюдаются |
| Рост RAM от 100k к 500k objects | Не более 64 MiB после стабилизации cache; данные роста хранятся на диске |
| P0/P1 на metadata-bound small-file наборе против исходного алгоритма | Цель не менее 3× end-to-end при той же целостности; отдельно показать сокращение requests |
| P2 batching против нового individual пути | Включать только при выигрыше ≥15% и допустимой latency регрессии по S07 |
| Телеметрия и UI | Не более 5% потери throughput на сопоставимом стенде |

Цели по wall-clock — критерии конкретного стенда, не обещание времени на неизвестной SFTP-инфраструктуре. Если физический backend объективно ограничивает 3×, отчёт обязан показать измеренный потолок и сохранённые структурные улучшения; нельзя пройти приёмку простым увеличением скрытого буфера или выключением verification. До выяснения bottleneck автоматическое увеличение concurrency не принимается.

### 11.5. Артефакты испытаний

Сохранять version manifest, dataset manifest, настройки, before/after метрики, сырые интервальные результаты, список injected faults и итоговые content verification. Отчёт должен различать preliminary benchmark и production canary. Фактические результаты не заполнять вымышленными числами из целей выше.

## 12. Внедрение, продолжение текущей загрузки и откат

### 12.1. Контрольные точки

| Gate | Работы | Условие перехода и сохранённый результат |
|---|---|---|
| G0 — верификация базы | Зафиксировать версии/хеши, стадии, query plans, файловое распределение, лимиты и возможности backend | Diagnostic bundle + исходные метрики + согласованная backup-копия профиля |
| G1 — безопасные быстрые исправления P0 | Прямой child lookup, уникальные родители, устранение лишнего хеширования, streaming scanner, постоянные операции, bounded workers, адресные ошибки | Нет повторной подготовки всего дерева после restart; сохранён backend verification; безопасная передача большого root без старого обязательного финального PROPFIND |
| G2 — постоянная модель и серверная история P1 | L/B/R, общий mutation core, root journal, consistent snapshots, статус по операциям, conditional publication | Пройдены journal/snapshot/CAS/crash tests; old and new paths не обходят core |
| G3 — локальная дельта P1 | USN, watcher dirty queue, generations, gaps recovery; обычный цикл без per-file HEAD | A02/A03/A08/A15/A20/A21 и canary на втором ПК |
| G4 — массовая передача P2 | Small-file batches, batch commits, clone при capability, adaptive concurrency | Performance gates S07/S09, частичные отказы пакетов; rollout по root |
| G5 — backend acceleration / P3 | Storage-local verify, fencing-capable agent, delta/Merkle при доказанной выгоде | Дополнительные capabilities подтверждены тестами; generic SFTP fallback сохранён |
| G6 — production expansion | Продолжить основной root, проверить длительную работу и восстановление | Завершён bootstrap, steady state стабилен, rollback package сохранён |

P0 не обязан уже обеспечивать все steady-state свойства P1. До G2/G3 допустим временный legacy per-file check для ещё не перенесённых mappings, но он явно обозначен; критерий A02 относится к полностью включённому новому движку. P0 не включает удаления при неполном remote index. Если прежний финальный обход нужен старому delete-плану, его нельзя просто удалить и оставить прежние автоматические удаления: они отключаются до достоверного нового плана.

Стриминг S02 внедряется в P0; согласованный snapshot+feed зависит от S04 и завершён в P1. Это одна архитектура с поэтапным включением, не два параллельно пишущих движка.

### 12.2. Действия с работающим клиентом текущего ПК

Не удалять профиль и не запускать тот же exe снова ради «разгона». Сначала получить актуальную фазу: исходные 0 file records из ранней диагностики могли измениться. Зафиксировать counts prepared/published/partial, текущие ошибки и занятые ресурсы. Затем:

1. Штатно приостановить выдачу новой работы. Дать ограниченное время завершить безопасную часть, сохранить checkpoint; не заставлять пользователя ждать ещё сутки общего прохода.
2. Проверить, что процесс не продолжает писать профиль. Создать consistent backup через SQLite Backup API либо корректно остановленный набор DB/WAL; произвольное копирование только `neptune.db` при активном writer запрещено [W30].
3. Сохранить device identity, mapping, root bindings, конфигурацию, версию старого exe и серверные operation/checkpoint идентификаторы. Секреты хранить защищённо, не в открытом markdown/log.
4. На **копии** профиля выполнить миграцию и plan-only import серверного состояния. Не выполнять отправку/удаление из тестовой копии в production root.
5. Пройти canary на отдельном root и на малом устройстве; переключить исходный mapping через единственного writer, включив no-delete migration mode.
6. Импортировать существующие каталоги, принять совпавшие файлы, восстановить совместимые checkpoints и передавать разницу. Сверить итоговые receipts и manifest поддерживаемой области.

В текущем чате эти действия **не выполнялись**. Документ не останавливает процесс и не изменяет исходники; это runbook для реализации и обслуживания.

### 12.3. Миграция local database

Добавлять новое поколение таблиц/колонок и журнал миграции; не перезаписывать единственный экземпляр базы. Сохранённая `schema_version`, backup hash и migration manifest обязательны. Legacy rows без достаточного B помечаются `BASELINE_UNKNOWN`, не выдумывают версии. Directory records могут быть adopted после проверки ID/type/root; file records — по достаточному совпадению содержимого и согласованной remote version.

Старые partial uploads импортировать только если их format/source identity/серверная session совместимы. Несовместимый partial сохраняется как quarantined legacy temp до решения об очистке. Это не мешает принять уже завершённые файлы или каталог. Новые sessions используют отдельный namespace идентификаторов, чтобы не спутать intents двух версий протокола.

### 12.4. Безопасный откат

Feature rollback (выключение batches/delta/adaptation) предпочтительнее запуска старого бинарника: базовая новая модель состояния и журнал остаются. При необходимости бинарного отката остановить новый writer, сохранить новый профиль и server receipts, восстановить предыдущую **совместимую** схему/бинарник на отдельной копии. Откатить БД вслепую к моменту до новых публикаций и сразу включить старые удаления запрещено: server уже мог измениться.

После бинарного отката root остаётся no-delete и проходит adoption/reconciliation. Старый клиент, не понимающий новые versions/receipts, не получает право безусловной записи в уже мигрированный root. Для P0/P1 минимально поддерживаемая версия writer фиксируется на Saturn. Rollback без потери данных может означать временную паузу синхронизации, а не обязательно немедленное возвращение к старому протоколу.

### 12.5. Проектируемый CLI

Команды ниже задают ожидаемую поверхность CLI после реализации; **они не утверждаются доступными сейчас**.

```powershell
neptune sync inspect --profile default --mapping projects --json
neptune sync pause --profile default --mapping projects --checkpoint
neptune profile backup --profile default --consistent --output "D:\sync-backups\default-v1"
neptune sync migrate --profile default --mapping projects --plan-only
neptune sync adopt --profile default --mapping projects --no-delete
neptune sync resume --profile default --mapping projects
neptune sync status --profile default --mapping projects --stages
neptune sync reconcile --profile default --mapping projects --scope metadata --no-delete
neptune sync diagnostics --profile default --mapping projects --redact-secrets
```

`--plan-only` не делает серверных mutation. `adopt` не создаёт второй профиль/device и не принимает отличающиеся файлы автоматически. Для изменения правил и массового удаления CLI выдаёт plan hash и требует явного подтверждения именно этого плана. Команда очистки истории/temp не является побочным действием `resume`.

| S11 | Moves, conditional changes, guarded deletes | S01, S04, S05, S10 |
| S12 | Resumable recovery и отдельный scrub | S01, S02, S04; Merkle optional |
| S13 | Cost-gated block delta | S08/S10 + immutable base + supported backend |
| S14 | Authorized file-level reuse | Known hashes, S10/S11, clone capability |

S04 и S10 имеют совместный интерфейс, но не циклическую зависимость запуска: S10 сначала реализует intent/physical-result boundary, затем короткий metadata commit S04; передача не ждёт будущего feed, а запись feed использует уже готовый physical result.

### 13.3. Что должно быть в pull request и release package

Реализация каждого S/T сопровождается входной валидацией, migration/feature flag, адресными тестами, метриками и rollback-описанием. Для wire API требуются machine-readable OpenAPI/JSON Schema, golden tests C#↔TypeScript для integers64/hashes/name codec/canonical JSON и compatibility tests старого/new клиента. Схема в настоящем документе — нормативная основа для генерации этих файлов, не утверждение, что они уже созданы.

Уровень готовности: не только «быстрее на моей папке», а выполненные инварианты I01–I20, обязательные A-tests для включённой фазы, measured resource caps, сохранённые диагностические результаты и проверенное продолжение после остановки. Optional feature не должна быть условием базовой синхронизации, если существует описанный fallback.

### 13.4. Итоговая последовательность исправления

Сначала устранить существующие повторные path/parent операции и препятствие завершению большого дерева. Затем внедрить сохраняемое состояние и дельту объектов, чтобы повторная синхронизация перестала быть повторной инвентаризацией. После этого ускорять необходимые bytes: пакеты, справедливый ограниченный параллелизм, эффективный SFTP и проверка ближе к диску. Блочная дельта и content reuse подключаются там, где они сокращают полную стоимость, а не просто уменьшают один вид счётчиков.

**Целевой результат:** работа пропорциональна новым/изменённым объектам и действительно нужным байтам; уже подтверждённое не выясняется заново и не передаётся повторно; отказ останавливает конкретную операцию, не возвращает весь root к началу.

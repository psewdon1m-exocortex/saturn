# Manual reconciliation of an absent zero-offset backup part

`reconcileAbsentBackupPart` is a privileged offline operator boundary, never an HTTP request or lease-based takeover. It requires a trusted `OfflineBackendFence` implementation which performs fresh I/O on every invocation: authenticate to the original live supervisor, prove that its exact managed API and worker children have exited, match the supervisor PID/creation/image/command to a pinned identity and reject any live/reused child PID. A JSON receipt or PID absence alone is not an implementation of that contract. The operator must stop every other writer and preserve DB, original profiles/spools and evidence first.

Under exclusive maintenance it accepts only one unresolved UNKNOWN `delete` for an exact `service_backup_runs.temp_path` in the backup incoming namespace, with zero received bytes and a pending/uploading original. It verifies absence through an independent physical adapter and existing directory ancestors. A changed fence, any live reader, another unresolved operation, extant object, changed owner or transport/permission uncertainty refuses without committing.

The original task is retained as REJECTED_NO_TARGET, with the previous row/error and physical proof in `saturn_owner_recovery.history`. No write, delete or upload is replayed. A separately recorded owner release permits a fresh worker after the offline boundary. The original native spool and server run must then continue through ordinary public upload-offset/append/complete and independent full SHA readback. This manual result is not proof of automatic crash recovery, native completion, or release readiness.
